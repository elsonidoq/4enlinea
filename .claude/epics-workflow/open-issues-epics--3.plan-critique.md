# Plan critique — specs/053-entitlement-payments-consolidation

## Verdict on the flagged call (research.md Decision 1)

**The factual premise checks out.** `loadUser` (`connect-four/server/index.js:504-531`) issues a real per-request query — `supabase.from('users').select(USER_PROFILE_SELECT_COLUMNS).eq('id', ...).single()` — and `USER_PROFILE_SELECT_COLUMNS` (`connect-four/server/userHelpers.js:14`) does include `tier`. It is registered globally at `index.js:533`, i.e. **before** `registerUserRoutes` (line 536, where the new endpoint would live) and before `app.get('/api/lessons/:id')` (line 674). There is no memoization or per-user cache: every request re-reads the row. So `req.user.tier` is genuinely present and DB-fresh on both paths that matter. Reading `req.user` instead of issuing a second query does **not** reintroduce the staleness the epic exists to fix.

Two caveats, turned into Decision 1 and Blocking issue 2 below: (a) nothing structurally guarantees a future caller passes a DB-sourced object — `computeEntitlement(user)` has the same shape as the `getSubscriptionStatus({tier})` the epic dismisses as "no new authority"; (b) `loadUser` silently degrades *every* failure (missing token, expired token, DB error) to `req.user = null`, which the new gate reads as "not entitled."

## Blocking issues

**1. The plan orders an edit to `pricing.html` that the owner ratified as forbidden.**
`plan.md`'s Source Code map (the section `/speckit-tasks` reads to generate tasks) contains:
`│   └── pricing.html   # US4: served at /pricing-legal instead of /pricing; de-hardcoded figures`
The owner's 2026-08-01 decision — carried in the handoff, the epic's Acceptance criteria, and the spec at FR-020/FR-026/SC-004 and Assumptions — is the opposite: the retained legal page keeps its hand-typed price and quota literals, stays static, JavaScript-free and byte-stable, because the payment provider already reviewed that exact wording. De-hardcoding is scoped to `/pricing` only. Left as-is, a task agent will edit a page it must not touch and then mark OI-41 resolved, when the convention requires it to stay **open** with a dated `UPDATE` naming the remaining literals.
*Fix:* change that line to `# US4: route path only (/pricing → /pricing-legal); file content byte-stable, literals retained (owner 2026-08-01)`, and add an explicit note that OI-41's closeout is an UPDATE, not a RESOLVED flip. The rest of the plan (Summary, quickstart step US4.4) is already correct — this is one stale line, but it is the line the task generator consumes.

**2. US1 changes a response shape whose three actual consumers the plan never touches — and they crash on it.**
`GET /api/lessons/:id` is fetched by `src/screens/ConceptScreen.jsx:46`, `src/screens/SocraticScreen.jsx:38`, and `src/screens/CLChallengeScreen.jsx:27`. `ConceptScreen` then does `const slide = lesson.slides[slideIndex]` (line 166, also 78/89/100) with no guard — a `{ locked: true }` stub with no `slides` throws a TypeError, i.e. a blank/error screen. The constitution's Principle IV explicitly forbids that ("locked paid-tier content MUST always render a preview card... MUST NOT be invisible or produce an error"), and the plan's own Constitution Check cites this principle as satisfied. `plan.md`'s file map lists none of the three screens; `contracts/lessons.md` names only `CLChallengeScreen`, in prose. Not hypothetical: the guard that today prevents the fetch (`src/lib/useLessonLockGuard.js`) is client-side, and FR-013's new fail-open-to-last-known-good rule *deliberately widens* the window where the client believes "paid" while the server says "locked" (expired session, downgrade, stale cache).
*Fix:* add explicit tasks under US1 for all three screens to detect `locked === true` and render the existing upgrade-prompt affordance instead of indexing `slides`, plus one component test per screen. Add the three files to `plan.md`'s Source Code map so the task generator sees them.

**3. Three static legal pages link to `/pricing` and are not in the plan's touch list.**
`connect-four/server/privacy.html:45`, `terms.html:49`, and `refunds.html:34` each render `<a href="/pricing">Pricing</a>`. Once the React route takes over `/pricing`, those links resolve to the SPA shell — defeating the stated reason `pricing.html` is retained at all (a JavaScript-free, server-rendered copy of the Merchant-of-Record clause and refund statement reachable by a provider spot-check that may not run JS). Research Decision 6 found one previously-uncited navigation touch point (`LegalFooter.jsx`) but stopped at the SPA; these are three more, server-side. Editing them is permitted — only `pricing.html` itself must stay byte-stable.
*Fix:* add a US4 task re-pointing those three links to `/pricing-legal`, and a quickstart check that `/pricing-legal` is reachable by following a link from `/terms` with JavaScript disabled.

## Decisions required

**1. Should the entitlement module's exported production entry point take `req` rather than a loose `user` object?**
The plan's `computeEntitlement(user)` is a pure function over `{ tier }`. Behaviorally correct today, but textually the same shape as `getSubscriptionStatus({ tier })` — the function the epic rejects because its input carries no guarantee of DB provenance. Nothing stops a future call site from passing a client-supplied or cached tier, and the module's own unit tests will pass literals.
- *Option A (recommended):* keep the `req.user` design and the pure core, but make the **exported** production API `entitlementForRequest(req)`, with the pure `computeEntitlement(user)` kept internal/test-only and documented as such in `api-conventions.md`. Zero extra I/O; DB provenance becomes structural rather than a comment.
- *Option B:* make it async and query `users.tier` itself. Honors the epic's literal wording, but doubles the DB read on every gated request and adds a failure mode the plan would then have to fail-closed around.
- *Option C:* leave as planned. Cheapest, but relies on convention to hold a security boundary.

**2. Should the entitlement answer distinguish "signed out / session lapsed" from "signed in, free tier"?**
The plan has `GET /api/user/entitlement` always return `200 { entitled: boolean }` (research Decision 4), and the client fails open only on *fetch failure* (FR-013). An expired auth cookie produces neither: `loadUser` degrades it to `req.user = null`, the endpoint returns a perfectly successful `200 { entitled: false }`, and the client helper caches that as a valid answer — overwriting the last-known-good and downgrading a paying customer's UI to locked. Because the response is 200 and not 401, the existing one-shot refresh wrapper `src/lib/fetchWithAuthRetry.js` (which triggers only on `res.status === 401`) never fires, so the session is never repaired. Same applies to the locked lesson stub.
- *Option A (recommended):* add an `authenticated: boolean` field to the response, and have the client helper treat `{ authenticated: false }` while it holds a `lastKnownGood` of `entitled: true` as a session-refresh trigger (one `POST /api/auth/refresh` + retry, reusing `fetchWithAuthRetry`'s bounded pattern) before accepting the downgrade. Preserves the 200-for-anonymous convention the plan documented.
- *Option B:* route `getEntitlement()` through `fetchWithAuthRetry` and return 401 for anonymous callers, matching the standard `/api/user/*` invariant. Simpler, but reverses research Decision 4 and makes the anonymous locked-lesson-preview case an error branch.

Everything else — the no-HTTP-hop module/wrapper split, the fail-closed/fail-open asymmetry, the no-code-change identity ratification, the `/pricing` takeover mechanics via Express registration order, the five migration sites, the `npm run test:fast` and `dist/`-build CSP constraints — is present, correctly sequenced, and consistent with the epic.

## Handoff context

**Systemic issue:** the plan is strong on the *server* half of every seam and thin on the *client* half. Blocking issues 2 and 3 are the same failure repeated — a server-side change lands correctly, and the consumers that must absorb the new shape or the new URL are named in prose (or not at all) but never appear in `plan.md`'s Source Code map, which is the artifact `/speckit-tasks` turns into tasks. A fix agent should treat that map as the binding contract and reconcile it against every prose claim in `research.md`/`contracts/`. Research Decision 6 found one such omission (`LegalFooter.jsx`) by looking at the SPA; the same sweep was never run over `server/*.html` or over the lesson screens.

**Reviewer frame:** working tree above every document, then the owner's ratified decisions, then the epic, then the spec. `docs/open_issues.md` treated as history. Re-derived at source: `loadUser`'s body and registration order, `USER_PROFILE_SELECT_COLUMNS`'s contents, the lesson handler, the four `/api/lessons/:id` client fetches, `ConceptScreen`'s `slides` indexing, `fetchWithAuthRetry`'s 401-only trigger, `app.get('/pricing')` at `index.js:4088`, the catch-all at 4102, `URL_MAP`'s current entries, and the `/pricing` hrefs in the static legal pages. The epic's five tier-read sites and `getSubscriptionStatus`'s body were NOT re-verified — verified twice already in this chain, and not where the risk sits.

**Non-obvious intent a fix agent must preserve:** (a) the `/pricing-legal` page's staleness is *deliberate* — do not "improve" it; (b) the fail-open (client) / fail-closed (server) asymmetry is a requirement, not an inconsistency; (c) research Decision 1's `req.user` choice is sound and should not be flipped to a second DB query on the strength of the epic's wording alone; (d) `computeEntitlement` returning `false` for anonymous is intentional and must not be "fixed" into a 401 without addressing Decision 2's session-lapse case first.

**What was not flagged and why:** the 5-minute cache TTL (owner settled "short TTL"; any value in range works); the `GET /api/limits` endpoint (a genuinely new seam but well-justified — `FREE_DEEP_REVEAL_WEEKLY_LIMIT` is exported from `quotaLimits.js:5` and already imported at `index.js:58`, so the contract's implementation snippet is accurate); the OI-34 re-map to `verifyTransaction`; the manual-only CSP gate (matches project precedent); the `UpgradeModal` sub-component extraction question (a genuine implementation detail); and the stale task-count hints (explicitly non-binding).
