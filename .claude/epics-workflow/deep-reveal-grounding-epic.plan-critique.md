# Plan critique (Opus, source-verified) — specs/058-deep-reveal-grounding

## Blocking issues

**1. FR-011 (raw coordinates promoted, not flattened) has no implementation site, and its only possible site is a file Plan A owns.**
Settled decision 7, FR-011, US3 acceptance scenario 1, SC-002 and the quickstart all require that a bare `c1r3` left in the coach's prose becomes a real `[zone:c1r3]` highlight instead of the lossy "column 1". The *only* code that performs that flattening is `stripInternalTokens` in `connect-four/server/reasonRenderGuard.mjs` (`CXRY_RE`/`RANGE_RE`/`BARE_COL_RE`, each `.replace()` feeding the next) — and Cross-lane constraint 1 forbids this epic from touching `stripInternalTokens`/`RANGE_RE`. The plan's Summary names the promotion ("raw coordinates promoted, not flattened") but its Source Code file map assigns it to no file: the `reasonRenderGuard.mjs` entry says only "threads allowedSet … NOT touching stripInternalTokens/RANGE_RE". Per the project's own rule that the plan's file map is what `/speckit-tasks` reads, this requirement will silently receive zero tasks. **Fix**: add an explicit entry — a *new* exported function (e.g. `promoteRawCoordinates(text)`) in `reasonRenderGuard.mjs`, called from `guardExplainMoveLlmPayload` before `stripInternalTokens`, leaving Plan A's two symbols byte-identical — and state the ordering constraint (promotion must run before flattening, and must skip zone-tag delimiters via the existing `ZONE_TAG_RE` split, or it will corrupt `[zone:cells:c4r1,c4r2]` exactly as that file's comment warns).

**2. US3's `checkP5Strong` wiring is partial in two more ways the plan did not catch — the same class of gap it correctly caught for `windows:`.**
- *Nothing gets stripped.* `stripFailingZoneSpans` only acts on codes in `SPAN_CARRYING_CODES = new Set(['P1','P2','P5','P6'])` (`reasonRenderGuard.mjs`). Every code `checkP5Strong` emits is prefixed `P5strong:` (e.g. `P5strong:cell_not_allowed:c4r3`), which is **not** in that set. Once `allowedSet` is threaded, an ungrounded highlight will mark the payload invalid, emit a `console.warn`, and then be **served to the player unchanged**. FR-012, US3 scenario 2, SC-006 and the quickstart ("the second is caught and stripped") all fail. Fix: add `P5strong` to `SPAN_CARRYING_CODES` and make it an explicit task with a test.
- *`future:` specs bypass P5Strong entirely.* The plan asserts that stripping the `future:` prefix inside `zoneParser.js`'s `isValidSpec`/`expandSpec` means "P1/P5/P5Strong validate `future:` specs for free, no separate change." Verified false: `checkP1`, `checkP2` and `checkP5` do call `isValidSpec`/`expandSpec`, but `checkP5Strong` matches the raw spec string with its own regexes (`/^col(\d+)$/`, `/^c(\d+)r(\d+)$/`, `/^cells:(.+)$/`, `/^row(\d+)$/`) and never calls either helper. A `future:c2r6` spec falls through every branch and is never checked — the identical silent-fallthrough bug the plan diagnosed for `windows:`. Since US1 exists to create `future:` specs and US3 exists to ground them, this must be one task with the `windows:` branch.

**3. The required-set compliance check, as specified, can never pass — it would retry and log a failure row on every single request.**
`data-model.md` §2 defines the retry trigger as "checks every `requiredSet[].handle` appears as `[zone:{handle}]` in `attempt.mechanism`". But `runLlmAttempt` calls `postprocessAnswer` → `processAnnotations`, which does `text.replaceAll('[zone:'+handle+']', '[zone:'+spec+']')` before `computeMechanism` ever sees `attempt.mechanism`. By that point no handle survives — only expanded specs. `research.md` D3 hedges ("or its already-expanded `spec`, post `processAnnotations`") and `plan.md` doesn't pin it at all, so the artifact a tasks author will treat as the contract is the wrong one. **Fix**: state in plan.md and data-model.md that the check is against `[zone:{spec}]` on the post-`processAnnotations` mechanism (or, better, against `processAnnotations`'s existing `usedSpecs` — noting the epic's own warning that `usedSpecs` is a local, not part of the return shape, so it must be surfaced).

## Decisions required

**1. Where does raw-coordinate promotion live, given Plan A owns `stripInternalTokens`?**
- (a) New `promoteRawCoordinates()` in `reasonRenderGuard.mjs`, called from `guardExplainMoveLlmPayload` before `stripInternalTokens`. Same file, different symbol — honours constraint 1 literally, but merges into a file Plan A is actively editing.
- (b) Hand FR-011 to Plan A and drop it from this spec's scope. Zero conflict, but leaves US3 half-delivered and SC-002 unowned.
- (c) Promote in `server/index.js` before calling the guard. No file conflict at all, but splits one text-sanitization concern across two modules and skips the two non-fresh response branches (cache hit, not-a-blunder).
- **Recommend (a)**.

**2. Does promotion run before or after the annotation gate?**
A promoted coordinate is, by construction, one the coach was *not* offered a handle for — so if promotion runs before `validateAnnotation`, `checkP5Strong` will (once issue 2 is fixed) correctly strip it right back out, and FR-011 delivers nothing. If it runs after, an ungrounded cell reaches the board as a real highlight — precisely the failure mode US3 exists to prevent.
- (a) Promote first, validate second, and on a P5Strong rejection fall back to today's "column N" flattening for that one coordinate.
- (b) Promote after validation, unconditionally (FR-011 wins, FR-012 is bypassed for promoted cells).
- **Recommend (a)**.
