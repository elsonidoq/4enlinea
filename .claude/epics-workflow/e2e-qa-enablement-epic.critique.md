# epic_critique output

## Blocking issues

### 1. Settled decision 7's stated reason for the HTTP endpoint is factually wrong — `invalidateEntitlement()` is browser-side code, so no server endpoint can call it

Decision 7 justifies the dev-only endpoint this way: *"so the server can call `invalidateEntitlement()` in the same request (this is what AC2's 'observable without DevTools' requires, per NF2)."* That function is client-only: `connect-four/src/lib/entitlement.js:58`, in a file whose header reads *"Client-side entitlement cache"*, and its only importers are `src/lib/useUpgradeCheckout.js` and `src/store/ProfileStore.jsx`. There is nothing named `invalidateEntitlement` anywhere under `connect-four/server/`. A server route physically cannot reach the module-level variables living in the browser tab's JS. So AC2 ("a previously-Pro screen renders free-tier UI with no manual DevTools intervention") has, as written, **no working mechanism**.

Two further details the spec will get wrong if this is not fixed now: (a) even in the browser, `invalidateEntitlement()` is the *weaker* of the two resets — it only zeroes the TTL (`lastFetchedAt = 0`) and deliberately keeps `lastKnownGood`, and the fail-open branch documented at `entitlement.js:66-75` can then **re-pin a stale `entitled: true`** after a downgrade. The correct call after a rollback is the hard reset `clearEntitlement()` (`entitlement.js:77`), which is exactly what sign-out already uses (`ProfileStore.jsx:110`). (b) The endpoint is still worth having for other reasons (an agent driving Chrome can hit it without a shell), so the *decision* stands — only its rationale and AC2's mechanism need repair.

**Recommended resolution:** rewrite decision 7's parenthetical to drop the server-calls-`invalidateEntitlement()` claim, and re-anchor AC2 on a client-side step: either the documented page reload (which discards the module cache wholesale and is already how the dev reset works, `SettingsScreen.jsx handleDevReset` ends in `window.location.reload()`), or a dev-gated button that calls `clearEntitlement()` — never `invalidateEntitlement()` — and refetches. Note the epic's own memory reference `project_entitlement_client_cache_traps` says the same thing.

### 2. Settled decision 8's synthetic events cannot affect the QA user's row as specified, and cannot be replayed on run N+1

Three mechanical facts, all verified in `connect-four/server/paddleProcessor.js`, that the epic does not account for:

- **Targeting.** Subscription events carry no user id; the tier write is keyed by customer: `await writeTier({ customerId, tier: 'free' })` (`paddleProcessor.js:391`, `:399`), and `writeTier` does `query.eq('paddle_customer_id', customerId)` (`:172-175`). A payload *harvested* from some earlier real sandbox event carries **that** event's `customerId`, which will not equal the `paddle_customer_id` this QA run's checkout just wrote. Supabase returns no error when an UPDATE matches zero rows, so the webhook answers 200 `{received:true, handled:true}` while nothing changed — AC3a's "verified against the `users` row" would fail confusingly, or worse, pass a test that asserted only the HTTP response.
- **Replay.** `payment_events.event_id` is UNIQUE and the insert happens before any tier write; a `23505` short-circuits to `{ handled: false, eventType: 'duplicate' }` (`:302-306`). The *same* harvested payload sent on run N+1 therefore does nothing at all — a direct conflict with AC1 ("runs twice back-to-back and produces the same pass/fail per CTA"). The `event_id` must be re-stamped per send, or rollback must delete the run's `payment_events` rows (which the epic does not list among rollback's duties).
- **No identified harvest source.** The binding constraint says payloads "MUST be harvested from a real Paddle sandbox event", but no such event has ever been received: `connect-four/server/.env` carries the comment *"sandbox account has no public tunnel — Paddle cannot actually deliver to it"*, and the local `payment_events` table is empty (queried: `[]`). The epic asserts a constraint whose input does not yet exist anywhere the spec author can find it. (Signature freshness is a fourth, smaller item: `webhooks.unmarshal` enforces a timestamp variance window, so the harness must re-sign at send time regardless.)

**Recommended resolution:** add a short paragraph under decision 8 stating (i) the explicit, closed list of fields the harness is *allowed* to substitute into a harvested payload — `data.customerId`, `data.id`/subscription id, `event_id`, `occurred_at`, and the signature timestamp — with everything else verbatim, so "harvested not authored" keeps its meaning without being unusable; (ii) that the harness re-signs at send time; and (iii) a named harvest source with a fallback (first choice: complete one real sandbox purchase, then pull the subscription entity / notification log via the `paddle-sandbox` MCP; fallback: make "identify and record the harvest source" an explicit first task of the US covering AC3a, with the harvested payloads checked into the repo as fixtures so later runs don't re-harvest).

### 3. Decision 9's email seeding is not a frontend-only change — `users` has no email column, and the seeded email probably cannot be un-set

The epic's Lane paragraph assigns decision 9 to `AuthModal.jsx` + `SettingsScreen.jsx` only, and decision 7 requires rollback to "clear any dev-seeded email". But the email does not live where the epic implies:

- `public.users` has **no** `email` column. Queried live on this worktree's DB, the column list is: `id, device_uuid, tier, deep_reveal_count, deep_reveal_reset_at, paddle_customer_id, created_at, updated_at, streak_count, last_active_date, sparring_record, papergames_id, last_import_at, onboarding_status`.
- `req.user.email` — the value that decides the checkout branch — comes from the Supabase **auth** user: `req.user = profile ? { id: data.user.id, email: data.user.email, ...profile }` (`connect-four/server/index.js:547`), where `data.user` is the result of `authClient.auth.getUser(token)`.

Consequences the spec must have up front: setting an email on an *anonymous* Supabase user from the browser (`supabase.auth.updateUser({email})`) goes through a confirmation round-trip and does not take effect immediately — the reliable path is a service-role `auth.admin.updateUserById(id, { email, email_confirm: true })`, i.e. **a server endpoint** (`requireLocalhost`, same seam as decision 7), not just a button. And Supabase does not support clearing an auth user's email back to null, so decision 7's "clear any dev-seeded email" is likely unimplementable as literally written.

**Recommended resolution:** extend decision 9 to say the affordance is a dev-gated *button plus a `requireLocalhost` endpoint* using the service-role admin API, and add it to the Lane's file list. Replace "rollback clears the dev-seeded email" with the mechanism that actually works: the documented dev reset (`SettingsScreen.jsx handleDevReset` -> `POST /api/auth/signout` + storage clear + reload) means the next `Dev: skip auth` calls `authClient.auth.signInAnonymously()` (`index.js:507`), which mints a **brand-new** auth user and a brand-new `users` row — so the email is gone by construction. Rollback's job on the email is then "none, provided the reset ran"; if that is right, say so explicitly so the spec doesn't invent an un-set path.

## Decisions required

### D1 — Does one QA run use one account throughout, or a fresh account per CTA?

**What this refers to:** the epic's NF1 is called "the highest-risk fact in the epic": a rollback that sets `tier='free'` but leaves `paddle_customer_id` populated makes run 2's payment silently rejected by the security check at `paddleProcessor.js:353-360`. That failure mode requires the *same* `users` row to survive into run 2. But the epic's own Settled decision 4 makes the dev reset the standard between-test reset, and that reset signs out and reloads — after which dev-skip-auth mints a **new** anonymous auth user and a **new** `users` row (`tier` free, `paddle_customer_id` NULL). Under that flow, NF1's trap never fires, and the "first payment for this userId" branch is trusted every time. The two statements are both in the epic and they point at different amounts of work for US1.

- **Option A — one persistent QA account for the whole payment journey** (reset only between the *auth* CTAs, not between the 6 checkout CTAs). NF1 binds fully; rollback must null `paddle_customer_id`, cancel the sandbox subscription, and clear `payment_events` for replayability. Most faithful to how a real user behaves; the epic as written assumes this.
- **Option B — fresh anonymous account per checkout CTA.** Cheaper: the DB half of rollback is nearly free, and US1 shrinks to Paddle-side cleanup plus the AC2 client-cache step. Cost: the second-payment security path (OI-55 hardening) is then never exercised by QA, and each of the 6 CTAs leaves an orphan sandbox subscription.
- **Recommended default: A**, with one explicit exception — the *auth* CTA sweep (AC4) keeps using the per-CTA dev reset, since it is testing routing, not tier. Then add one sentence to NF1 saying it binds *because* the payment sub-run deliberately retains one account.

### D2 — May the QA tooling cancel Paddle sandbox subscriptions unattended?

**What this refers to:** AC1 requires that after rollback "the Paddle sandbox subscription is canceled". Two frictions. First, mechanics: there is no subscription id stored anywhere — `users` has only `paddle_customer_id` (column list above), and no migration adds a subscription column — so the tool must list the customer's subscriptions through the Paddle API *before* nulling `paddle_customer_id`, an ordering constraint the epic never states (null it first and the id is unrecoverable). Second, policy: `CLAUDE.md` §"Paddle integration", which the epic itself lists as an authoritative source of truth, says *"For destructive account changes (updating prices, archiving products, canceling subscriptions), ask for explicit confirmation before calling the `paddle-sandbox` or `paddle-live` MCP server."* An unattended QA rollback that cancels subscriptions is, as written, a violation of a standing rule.

- **Option A — carve out a narrow, written exception:** sandbox only, only subscriptions whose customer id matches the QA user's row, cancellation performed via the Paddle **SDK** in the rollback module (not the MCP server, which is what the rule actually governs), with a `--yes` flag required for non-interactive runs. Record the lookup-then-null ordering in the epic.
- **Option B — don't cancel; leave sandbox subscriptions orphaned** and drop that clause from AC1. Simplest, and pre-launch sandbox residue costs nothing; the price is a slowly growing pile of active sandbox subscriptions and no coverage of the cancel path.
- **Recommended default: A.** It keeps AC1 intact, the exception is genuinely narrow, and it also gives the harvest source that blocking issue 2 needs (a canceled sandbox subscription is exactly the event AC3a wants to replay).
