# Epic critique (Opus, source-verified)

## Blocking issues

**1. US1 asks for exactly the handles a settled design decision deliberately forbids — and the doc holding that decision is not listed as a source of truth.**

Background: when the AI coach writes a deep-reveal explanation, the server first hands it a closed menu of board regions it is allowed to highlight ("handles"). That menu is built by `buildAnnotationOffer` in `connect-four/server/scripts/reason_engine/zoneAnnotations.mjs`. US1's premise is that the model "had no legal way to highlight the winning line or the key square" and that the menu should be widened.

But the menu's narrowness is intentional and documented. `zoneAnnotations.mjs` (constant `STRUCTURAL`, and the comment block above it) excludes the fork/`figure_7` cells the engine names, with the rationale: *"they often name a resource that completes deep, and highlighting a deep, currently-empty square is exactly the eval-3 present-threat trap decision #5 forbids."* The governing design doc `docs/architecture/reason-render-grounded-prompt.md` (§"Structural-only highlights", and §③ *"keep deep-horizon cells OFF the current board — they are empty now, so marking them invites the exact 'present-threat' error"*) says the same. The epic's own evidence row for `3154442332131341225551` cites `forkCells: ["c2r6","c5r5"]` as the answer the user wanted highlighted — those are precisely the excluded cells.

This is not a small conflict: it means US1 is a request to reverse a prior decision, and US2 (which requires the model to build the explanation around the load-bearing cells) is unsatisfiable on exactly the boards in the epic's evidence, because the required groups would have no legal handle. `reason-render-grounded-prompt.md` — the single most relevant design document for this epic — does not appear in the epic's `Authoritative sources of truth` list, so a fresh-context spec author would never see the conflict.

*Recommended resolution:* add `docs/architecture/reason-render-grounded-prompt.md` to the sources list, and add a settled decision that states explicitly whether deep (not-yet-playable) fork cells may now be offered as handles, and if so what prose framing prevents them reading as present threats. Without that, US1 and US2 cannot be specced.

**2. Two of the three "verified at source" facts the reading contract flagged are wrong, and the spec will inherit them verbatim.**

- *"`renderReasonModel.mjs:235` drops `zoneAliasMap` … it is why `checkP5Strong` receives a hardcoded `null` allowed set and never runs."* The drop is real (`zones: { aliases: zones.aliases, terms: zones.terms }`), but it loses **no information**: each entry in `aliases` already carries its `spec` field (`buildAnnotationOffer` pushes `{handle, spec, role, truthBoard, kbId}`), and `processAnnotations` reconstructs the same map from `aliases` alone. The real reason the grounding check never runs is that the live serving handler in `connect-four/server/index.js` never builds an allowed set at all and `guardExplainMoveLlmPayload` (`server/reasonRenderGuard.mjs`) passes a literal `null` — as that function's own header comment states. Restoring `zoneAliasMap` is therefore not the fix and would be wasted work; threading a set derived from `aliases` into the guard is.
- *"`[zone:col4]` and `[zone:col2]` are not offered handles and reached the user anyway … Do not assume the existing drop path works — characterize it before relying on it."* This is inverted. `col4` is not a handle at all; it is the **expanded spec** of the offered handle `better-col`/`played-col`, and `processAnnotations` rewrites handle → spec by design (`text.replaceAll('[zone:'+handle+']', '[zone:'+spec+']')`). Seeing `[zone:col4]` in the cached text is evidence the pipeline worked, not that the drop path leaked. The epic converts a healthy signal into an investigation task.

*Recommended resolution:* rewrite both bullets. State the allowed set is derivable from `aliases[].spec` with no `renderReasonModel` change, and delete the "characterize the drop path" instruction (or replace it with a real, still-unverified concern if one exists).

**3. The central mechanism of US2 — how the "required" cell groups get chosen — is not derivable from the code the epic points at.**

Settled decision 2 says the required set comes from `classifyCausalLink`, because "the link names which halves are load-bearing (`lostResource`, `opponentPunishment`)". At source, `classifyCausalLink` (`server/scripts/reason_engine/causalLinks.mjs`) returns `{ id, confidence, covers, guardrail, text }`. `covers` is a list of *field-name codes* (e.g. `'lostResource.terminal'`, `'opponentPunishment.kind'`), and every link lists **both** halves — so it cannot discriminate which half is load-bearing, and it names no cells. Getting from there to a set of 1–3 offered handles requires a new mapping (half → cell → offered spec) that the epic describes as "a flag plus a comparison, not new machinery". Relatedly, the epic states `processAnnotations` "already returns … the used-spec set"; it actually returns `zonesEmitted` (a boolean) and `keyCells` (specs already expanded into individual cells) — the spec set itself is a local variable.

*Recommended resolution:* replace the hand-wave with an explicit derivation rule (which field of which half yields a cell, how that cell is matched to an offered handle, and what happens when the match fails), and correct the `processAnnotations` return-shape claim.

## Decisions required

**1. The epic depends on a "small-fixes plan" that does not exist anywhere in the repository.** The epic's `NOT included` section excludes two bugs — the coach *speaks* raw internal coordinates ("c1r3") while the screen shows readable text, because the text-to-speech endpoint reads the unsanitized cached text; and the coordinate-range cleanup regex only matches an ASCII hyphen, so the model's typographic en-dash slips through — saying both "ship first, in the small-fixes plan". A repo-wide search for that plan returns only the epic itself and its handoff note. Both bugs are confirmed real at source. Options: (a) fold both fixes into this epic as a US0; (b) have the owner commission the small-fixes plan and make it a stated hard prerequisite with an ordering gate; (c) drop the dependency and accept that acceptance criterion 2 ("no raw square reaches the client") passes on screen while the coach still speaks them aloud. *Recommended default:* (a).

**2. Does board numbering (US4) apply only to the deep-reveal screen, or everywhere?** The board component the epic names is shared by 17 screens across gameplay, challenges, lessons, and admin tools. The acceptance criterion scopes numbering to "the deep-reveal board", but the epic gives no mechanism (a new opt-in prop vs. a global change), and the quoted user request — *"the board should have numbered columns and rows"* — is not obviously deep-reveal-specific. Options: (a) opt-in prop, deep-reveal only; (b) opt-in prop, enabled on deep-reveal now with the others deferred; (c) on everywhere by default. *Recommended default:* (b).
