## Brainstorm agenda

### 1. What "one tier-check interface" actually is — and whether the seam doc's warning still stands

- **Topic** — The shape of the single "is this user paid?" answer that all four paywall gates will call: a fresh server round-trip, a cached-with-refresh client store, or a token claim.
- **Type** — `technical-tradeoff`
- **Why it blocks speccing** — US3.2 says "design the interface (server-authoritative, with a defined client caching/refresh story)" but neither the epic nor any doc defines that story, and the four consumers are all *client* components (`src/screens/sagaLock.js:13`, `PostSetSummaryScreen.jsx:55`, `CheckoutReturnBanner.jsx:72`, `SettingsScreen`'s Subscription section). More importantly, the two sources of truth are in direct conflict:
  - `docs/open_issues.md` OI-39: *"Routing them through a server-side interface from the frontend is an architecture decision needing its own brainstorm"* — and *"Do not refactor the three call sites to close this issue."*
  - `docs/architecture/server-conventions.md` §PaymentProcessor Seam: *"`getSubscriptionStatus` is deliberately test-only in production wiring… do not 'fix' it by wiring a call site unless a new requirement actually needs a derived (non-`tier`) subscription status."*

  And the function itself is not a server check at all — `connect-four/server/paymentProcessor.js:47` is `export function getSubscriptionStatus({ tier }) { return { status: tier === 'paid' ? 'paid' : 'free' }; }`: pure, synchronous, no DB read, `customerId` ignored. Building US3.2 "on top of `getSubscriptionStatus`" as the epic instructs therefore delivers *no* new authority unless the interface is redesigned to actually read the DB. Spec this wrong and you either ship a rename that changes nothing, or add a network call to four render paths (including a modal that polls during checkout return) and re-plan.
- **Options / directions**
  1. **Doc-and-consolidate only** — one shared client helper reading `store.getProfile().tier` (the tier source `frontend-conventions.md` already mandates), refreshed by the existing auth/profile flow. Cheapest, zero latency, no new endpoint; leaves the "server-authoritative" wording of spec-045 item 12 formally unmet. *Trade-off: closes the duplication, not the authority gap.*
  2. **New `GET /api/user/entitlement` endpoint** reading `users.tier` server-side, with a short-TTL client cache + explicit invalidation on checkout return. Genuinely authoritative; costs a round trip per gate and needs an offline/failure policy (fail-open shows paid content, fail-closed locks paying users out). *Recommended default* — it is the only option that also serves US3.1's server-side lesson gate from the same code path, which is the epic's stated goal ("client and server cannot drift").
  3. **Server-only authority** — stop gating in the client entirely; every paid surface is a server response that simply omits paid content. Strongest, but rewrites five screens' UX (no "upgrade to unlock" affordance without a tier signal).
- **Seed question for the owner:** is "server-authoritative" a real requirement here, or was it aspirational spec-045 wording that `server-conventions.md` has since walked back?

### 2. The first-payment forgery window on the money path

- **Topic** — Accept the residual risk that a forged `customData.app_user_id` on a user's *first-ever* payment grants paid tier to an arbitrary account, or close it with a server-minted Paddle customer id at checkout time.
- **Type** — `product-decision`
- **Why it blocks speccing** — This is the difference between US3.3 being a documentation task and being a change to `createCheckout` + the webhook + a schema/backfill for `users.paddle_customer_id`. The epic's Settled decision #4 explicitly refuses to settle it: the shipped 2026-07-18 hardening was *"chosen unilaterally because no human was available to make the product-risk call the issue originally asked for — treat it as a proposal to sanity-check, not settled policy."* `server-conventions.md` §"Identity binding on `transaction.completed` (OI-55)" repeats the same disclaimer. No agent can legitimately make this call.
  Context for the decision: today, repeat payments are cross-checked against the stored `users.paddle_customer_id` and a mismatch silently skips the tier grant; a *first* payment has nothing to check against, so it is trusted. The attack costs the attacker real money to upgrade **someone else's** account — the incentive is unclear, which is why it was deferred.
- **Options / directions**
  1. **Accept and document** — record in `server-conventions.md` that the trust model is adequate for this app's risk profile (an attacker paying to benefit a stranger). Zero code. *Recommended default*, given the inverted incentive. *Trade-off: an attacker could grief-grant, or launder a chargeback-able payment onto a third-party account.*
  2. **Server-minted customer id at checkout** — `createCheckout` creates/looks up the Paddle customer for `req.user.id` (it already receives `userId` and currently drops it) and passes the customer id to the overlay; the webhook then binds on a server-established id from the very first event. Closes the window properly. *Trade-off: touches the live checkout path, needs a Paddle API call per checkout, and any new checkout surface re-opens CSP discovery (which took five rounds).*
  3. **Post-hoc detection** — keep the current model but alert/quarantine when a first-payment grant lands on an account with no session activity. Cheap, but is monitoring, not a fix.

### 3. Where the real pricing page lives — Express static page vs. SPA route

- **Topic** — Rebuilding `/pricing` as a product surface, given it currently sits *outside* the React app.
- **Type** — `technical-tradeoff` (with an open-design component)
- **Why it blocks speccing** — `connect-four/server/pricing.html` is a 50-line, JS-free legal-style page served by `server/index.js:4088` via `res.sendFile`, sharing `/legal.css` with `terms.html`/`privacy.html`/`refunds.html`, with `$2.99` / `$21.99` / `39%` / `$1.83` written as literal HTML. Every reusable asset for the epic's requirements lives in React and cannot be imported into it: `src/lib/usePaddlePrices.js` (fetches `GET /api/paddle/config`, `formatPrice`, `computeAnnualSavings`), `src/components/UpgradeModal.jsx` (287 lines, already has the monthly/annual toggle, savings badge, and i18n), and `src/lib/useUpgradeCheckout.js` (opens the Paddle.js overlay). US3.4's eight tasks — live prices, voseo Spanish copy, a CTA into checkout — are essentially impossible on the static page and essentially free on an SPA route. Picking wrong means writing all eight tasks against the wrong surface.
  The constraint that makes this non-obvious: Paddle domain review requires the page to be **publicly reachable** and to carry the Merchant-of-Record clause, the 14-day refund statement, and the `/terms` link verbatim (epic Settled decision #3). Whether a client-rendered SPA route satisfies a human/automated reviewer is exactly the kind of premise this project has been burned by before.
- **Options / directions**
  1. **SPA route `/pricing`** (Express handler yields to the catch-all) — reuses every existing component, live prices, full i18n, one-click into the existing checkout. *Trade-off: content is JS-rendered; must be re-verified against Paddle domain review, and a new checkout entry point re-opens CSP discovery.*
  2. **Keep the static page, de-hardcode it** — add a small vanilla-JS fetch of `GET /api/paddle/config` (already public, no credentials) plus the `FREE_DEEP_REVEAL_WEEKLY_LIMIT` figure, and style it. Guaranteed-safe for domain review; kills the drift bug (OI-41's "more dangerous half"). *Trade-off: duplicates price-formatting logic outside React, no real CTA, no i18n framework. **Recommended default** if domain-review risk is judged unacceptable.*
  3. **Both** — static `/pricing` stays as the reviewer-facing compliance page (de-hardcoded), and a designed in-app pricing/plan screen becomes the user-facing funnel. Highest cost, but decouples the compliance constraint from the product surface.
- **Seed questions:** is the pricing page meant to convert (a funnel entry) or to comply (a reviewer artifact)? Should it reuse `UpgradeModal`'s look, or is this the moment to design a plan-comparison surface the modal later adopts?
