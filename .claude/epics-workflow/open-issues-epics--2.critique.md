# Epic 2 — epic_critique output (verbatim)

## Blocking issues

**1. US2.3 (`drawing_move`) has an unnamed, undersized blast radius — it is a schema + vocabulary change, not a 6-task code tweak.**
OI-48's complaint is that a move which throws away a forced win is labelled "drawing move". The epic frames the fix as "add a 'forfeited a forced win' case upstream of `llmCoachHelpers.js`". Verified in the tree, that framing is wrong in three ways:
- There are **two independent producers**, not one. `classifier.js:737` (`classify()`, the live sparring path — `if (score === 0) return { tag: 'drawing_move' }`, with no look at the pre-move best score at all) is the *actual* OI-48 near-empty-board repro. `classifier.js:2063` (`tagBlunder` Phase E) already computes `preScore > 0 && postScore === 0` and *deliberately* calls that `drawing_move`. The epic names neither; a spec written from the epic alone will likely patch only the blunder path and leave the reproducing path untouched.
- `drawing_move` is a member of a **closed 16-tag set** enforced in four places: a Postgres CHECK constraint (`server/migrations/052_blunders_parity_threat_tags.sql`, superseding `032`), `server/blunderTags.js`, plus `data-model.md`/`db-schema.md`/`server-conventions.md:142`. Introducing a distinct tag therefore needs a migration, a stored-row backfill, i18n phrase pools in both locales (`src/i18n/en.json:894`), `blunderReasons.js`, `explainContext.js:415`, and the feature-vector glossary entry (`feature-vector-glossary.md:337`). None of this appears in the epic, and the epic contains no decision on whether a new tag is minted at all versus subdividing the existing one by `direction`/`reason`.
- "Wire it into the case taxonomy doc" is largely already done: `reason-case-taxonomy.md` already names `win_to_draw` (line 38) as a first-class case. The gap is the **tag**, not the case.
*Recommended resolution:* rewrite US2.3 to (a) name both producers by symbol, (b) add an explicit settled decision "new tag + migration" vs "same tag, refined direction/reason", and (c) if a new tag, list the six registry/i18n/schema touchpoints as tasks. Expect US2.3 to grow to 10–14 tasks.

**2. The epic's `Authoritative sources of truth` cites a document that does not exist, and omits the ones that actually arbitrate US2.2.**
The list says "`docs/knowledge-base/community-figure-7.md`, `allen-j-configuration.md`, the overcut/undercut entries". There is **no undercut KB entry** — `ls docs/knowledge-base/` shows `community-overcut.md` but nothing for undercut (a known repo trap; every entry is source-prefixed). Meanwhile US2.2 is entirely about Allen's transformation rules T2/T4/T5 (`classifier.js:341–378`, `isT4SameParity`/`isT5Exception`/`isT2Blocking`), and the canonical entries `docs/knowledge-base/allen-t2.md`, `allen-t4.md`, `allen-t5.md` — which carry the verbatim Allen quotes the rename decision must respect — are **not listed**. Conversely `community-figure-7.md` and `allen-j-configuration.md` are listed but map to detectors the epic explicitly puts out of scope.
*Recommended resolution:* replace "the overcut/undercut entries" with `community-overcut.md` + `allen-t2.md` + `allen-t4.md` + `allen-t5.md`, and point the undercut precedent at `docs/architecture/server-conventions.md:311` §"Undercut has two sides" (which is already listed and is the real undercut source of truth).

**3. US2.2's prescribed rename (`active_forcing` → "T5") contradicts the KB's own definition and would destroy the name the new case needs.**
The epic states the rename twice, as if settled: "rename `active_forcing` to name T5 either way". In code, `reason: 'active_forcing'` is indeed emitted on the `isT5Exception` branch (`classifier.js:1052`), so the label is misapplied — that much is true. But `docs/knowledge-base/community-overcut.md` defines *active forcing* as a genuine, distinct sub-case: "the current player plays into the column voluntarily with odd-column parity, blocking the opponent's lower threat and immediately threatening from R." That description is essentially the gravity-top-adjacent shape lesson 12 teaches and that OI-60 says the detector never matches. So the correct move is probably to **free** the name `active_forcing` for the new first-class branch and rename the T5 branch to `t5_row3_row6` — the opposite of what the epic instructs. As written, decision #3 in `Settled decisions` plus the US2.2 wording is a hard constraint that would push the spec into the wrong rename.
*Recommended resolution:* demote the rename from a settled instruction to an open question, and state both candidate label sets explicitly, citing the KB `statement` block.

## Decisions required

**1. Should the "gravity-top-adjacent overcut" that lesson 12 teaches become a real detector match, or should the lesson be re-scoped to what the detector actually finds?**
Background: `detectOvercut` (the code that recognises "my higher threat beats your lower one") only fires on three narrow Allen rule branches. The shape the overcut lesson actually teaches — the opponent's threat sitting directly beneath yours and immediately playable — is not one of them, so a learner is taught a pattern the product can never name back to them.
- *Option A — extend the detector* with a new branch for the adjacent case. Aligns product and engine; but overcut tags are stored and user-visible, and the pool is re-derived, so it is a content migration validated per `reason-INVARIANTS.md` I12 (full case space, one counterexample per branch).
- *Option B — re-scope lesson 12's copy* to the three cases the detector does find. Cheap, no stored-data impact; but it narrows a genuine strategic idea the KB documents as real.
- *Recommended default:* **Option A**, because `community-overcut.md` already documents the active-forcing sub-case as part of the concept — the detector is incomplete relative to the theory, not the lesson over-claiming. Note the mitigating fact below.

**2. Does OI-76 resolve by dropping the `perspective` argument, or by adding a child-position solver query?**
Background: `detectOvercut(board, scores, perspective)` reads one player's threats while gating on `scores`, which always belong to whoever is to move. When those two are different players, the answer is unsound. The identical bug was already fixed once for the undercut detector, by splitting it into two role-named functions that each anchor on the side to move and take no `perspective` at all.
- *Option A — mirror undercut:* drop `perspective`, split into victim/beneficiary roles. Small, precedented, documented at `server-conventions.md:311`.
- *Option B — keep `perspective` and query the child position* for the non-mover, following `detectForbiddenColumns`'s existing recursion. Preserves every call site's signature but adds solver calls.
- *Recommended default:* **Option A.** The blocking constraint is that `overcut` sits in `MISSED_OWN_PRIORITY` (verified: `classifier.js:1961`, evaluated on `moves + correctCol` where the tagged player is not the mover) — i.e. production *always* takes the unsound branch, so whichever option wins, stored blunder tags will change and every fixture diff must be read.
- *Materially reduces the risk on both decisions:* per OI-61's 2026-07-29 closeout, the local DB currently has **zero active `overcut` puzzle rows**, so US2.1's task "re-derive `highlight_metadata` for active `overcut` rows" is presently a no-op locally. Re-measure before planning around it; staging/production may differ.
