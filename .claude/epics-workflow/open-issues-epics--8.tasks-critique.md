## Blocking issues

**1. Four of the seven issues this epic exists to close are never actually closed — and one task forbids closing them.**
The epic's own acceptance criteria say: "Every `OI-N` under this epic's **Issues covered** is closed out in `docs/open_issues.md`… A shipped fix with a stale backlog entry is an incomplete story." The spec restates this as SC-005. Those seven issues are OI-70 (the broken lint gate), OI-71 (the hanging DOM test), OI-16 (the dead helper), OI-29 (the vacuous regression test), OI-58, OI-6, and OI-72. The task list contains closeout tasks for only the last three (T033 for OI-58, T036 for OI-6, T037 for OI-72). **OI-70, OI-71, OI-16 and OI-29 — the four the epic actually fixes with code — get no task that updates their backlog entry.** All four exist today as open headings in `docs/open_issues.md` (lines 2131, 2152, 390, 783). Worse, T046 is a final scope-police check that defines the *permitted* edit set as "OI-58/OI-6/OI-72 and the six T038-T043 issues, plus the T045 blockquote exception" — so an implementer following T046 literally would treat closing OI-70/71/16/29 as an out-of-scope violation and revert it.
*Fix:* add one closeout task at the end of each story (US1 → OI-70; US2 → OI-71, OI-16, OI-29) marking the entry ✅ RESOLVED with the date and the evidence that story produced, and amend T046's permitted-edit list to include those four.

**2. The eslint "base/catch-all block" (T005/T007) is not implementable as written, and contradicts T008's own acceptance checks.**
This is the highest-risk area, exactly as the handoff warned — no `eslint.config.js` code has been written or tested anywhere in this pipeline. The specific defect: under ESLint 9 flat config, config blocks *merge* — every block whose `files` glob matches a file contributes its `languageOptions.globals`. T005 asks for "a base/catch-all block (node globals…) covering every file not matched by the four scoped blocks," but a flat-config block has no way to express "not matched by another block" via a `files` glob. A literal catch-all (`files: ['**/*.{js,jsx,mjs,cjs}']`) with node globals would merge node globals into *every* file including `src/`, which directly breaks T008's own required assertion that `npx eslint --print-config src/components/Board.jsx` shows **no** `process` global. The task never says which mechanism to use (an explicit three-file `files` list, an `ignores` array on the base block, or a `globalIgnores`-style exclusion), so the implementer will guess, and T007's `--print-config` guardrail only checks that rules are non-zero — it will pass even in the broken-merge case.
*Fix:* rewrite T005 to specify the base block as an **explicit enumeration** — `files: ['vite.config.js', 'eslint.config.js']` with node globals, and a separate `files: ['public/sw.js']` block with browser + serviceworker globals — rather than a glob-based catch-all. Then make T008 the blocking gate for T005 (currently it reads as a verification afterthought), and require its four `--print-config` assertions to be pasted as evidence before T009 runs. Secondary defect in the same pair: T007 and T008 prefix their paths with `connect-four/` while the file header states commands run *from* `connect-four/` — as written every one of those seven `--print-config` commands would fail on a nonexistent path. Use the relative paths that `quickstart.md` already gets right.

**3. The lint-gate proof fixture is a violation the current config deliberately ignores — the SC-001/SC-001a proofs would report a false negative.**
`connect-four/eslint.config.js` sets `'no-unused-vars': ['error', { varsIgnorePattern: '^[A-Z_]' }]`. Both T017 and `quickstart.md` prescribe inserting `const _unused = 1;` as the "real violation" that must make `npm run lint` go red — but a name beginning with `_` matches that ignore pattern exactly, so lint stays green. T017 half-notices this (its parenthetical says "without the `varsIgnorePattern`-matching `_`/capital prefix") while giving `_unused` as the example anyway, and `quickstart.md` line 21 states it with no caveat at all. T020 then reuses "the same one-line violation" for the pre-commit-hook proof, so the same false negative propagates into the SC-001a evidence. The likely outcome is an implementer concluding the widened glob doesn't gate and burning time re-debugging a config that is actually correct.
*Fix:* replace the fixture in T017, T020 and `quickstart.md` with one that is genuinely reported under the current rule set — e.g. `const unusedProbe = 1;` (lowercase, no underscore) — and add "confirm the violation is reported by name in the eslint output, not merely a non-zero exit" to the task's success condition.

## Decisions required

**1. Does "wired into the test scripts" mean only `test:fast`, or `test` as well?**
The epic's acceptance criterion says lint must be "wired into the test scripts" (plural). The spec narrowed this to `test:fast` plus the pre-commit hook (FR-006), leaving the slower `test` and `test:dom` untouched, and T018 implements exactly that. This is a defensible reading — `test:fast` is the command CLAUDE.md designates for all regular development and CI — but it is a narrowing of the epic's wording that no artifact flags as a deviation (unlike the `tests/dom/**` scoping, which is flagged prominently in three places).
*Options:* (a) keep `test:fast` + pre-commit only, and add one sentence to the plan's "Deviations from epic decisions" recording it; (b) also prefix `eslint . && ` onto `test`. **Recommended default: (a)** — `test` is rarely run (it calls the real solver and hangs), so gating it adds no real coverage, but the narrowing should be recorded rather than left implicit.

**2. How far should FR-019(a)'s unused-binding cleanup reach into `src/` production components?**
FR-019(a) requires deleting every `no-unused-vars` violation — measured pre-split at 76, of which **34 sit in shipped `src/` React components**. This is by far the largest diff in an epic whose plan otherwise claims "no *behavior* change to any production code path," and the task list deliberately (and correctly, per the harvest-don't-invent rule) does **not** enumerate which 34 files those are — T011 defers the list to a fresh measurement at implementation time. So the epic's largest and riskiest edit is also its least bounded one, in a repo where other epics are concurrently editing `src/`.
*Options:* (a) do all 34 as specified; (b) fix `tests/`/`server/` (42 findings) now and demote `no-unused-vars` to `warn` inside the `src/` block with a tracking `OI-N`, mirroring exactly how FR-019(c) already handles `react-hooks`/`react-refresh`; (c) do all 34 but require them in a separate commit from the config change. **Recommended default: (c)** — the deletions are genuinely non-behavior-changing and worth doing, but isolating them in their own commit makes the "did lint's config change break something?" question answerable by `git revert` rather than by re-reading 34 diffs.
