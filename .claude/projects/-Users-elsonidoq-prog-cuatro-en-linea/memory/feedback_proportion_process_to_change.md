The owner wants heavyweight process rituals proportioned to the change. Concretely (2026-07-13):
when EDITING an existing skill with a small, additive change (e.g. adding a `--feature` mode +
generalizing one setup step to app-qa), he cut off the formal `writing-skills` RED-baseline —
"I think it is too much to do the red baseline protocol for this" — and chose "make the edit
directly, then validate it by using it on a real task." The GREEN validation was the actual
feature QA run through the improved skill.

**Why:** the `writing-skills` Iron Law ("no skill without a failing test first") and its full
pressure-scenario/rationalization-table ceremony are calibrated for *discipline* skills under
pressure; a small additive technique/reference edit doesn't warrant a fresh-context baseline
subagent when the gap is already unambiguous from the skill text.

**How to apply:** for a small additive skill/doc edit, state the concrete gap, make the change,
and validate it by exercising it once on a real task — don't spin up baseline + with-skill
subagent runs. Still keep the discipline for NEW discipline-enforcing skills and for behavior
that genuinely varies run-to-run. Same spirit as [[feedback_prework_discipline]] and
[[feedback_workflow_hygiene]]: empirical, lean, no ritual for ritual's sake.
