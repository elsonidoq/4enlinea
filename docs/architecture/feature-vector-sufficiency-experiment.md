## 1. Background / why this exists

The deep-reveal coach explains *why a move was a blunder*. The journey so far:

1. We iterated `run_eval.mjs` → `judge-deep-reveals` on the **production** pipeline
   (`buildExplainContext` → production prompt → `gpt-5.4-mini` → annotation gate). It did not
   reach acceptable quality.
2. We traced much of the failure to the **structured context** injected into the prompt, and
   reworked it into the **feature vector** (`toFeatureVector` in `server/explainContext.js`) —
   a compact, board-grounded projection, documented field-by-field in
   `docs/architecture/feature-vector-glossary.md`.
3. **This experiment** tests, *outside* the production explain implementation, whether
   **feature vector + glossary** is sufficient context to explain a blunder — with the end goal
   of arriving at a **prompt-building procedure that `gpt-5.4-mini` can handle**.

## 2. Goal, non-goals, and the trajectory

**Goal.** Determine whether the feature vector + glossary carry enough information for a model to
reconstruct the **correct, board-grounded reason** a move was a blunder — and, where it does not,
produce a **counterexample list attributing each failure to a missing/ambiguous field** so the
vector/glossary can be improved.

**This is a floor test.** We deliberately start with a model **more capable** than production
(`gpt-5.4` full vs. production `gpt-5.4-mini`, **same vendor/family** — OpenAI — so capability is
the only variable; see §6). Logic: if even the strong model cannot make a case crystal-clear, it
is **definitely a context blindspot**, not a capability gap. Success at the top is a *necessary*
condition for the weaker production model.

**The end goal is a trajectory, not a one-shot check.** Once the strong model passes reliably,
dial the model **down** toward `gpt-5.4-mini` while evolving the **prompt-building procedure**
**up**, until mini passes. The apparatus must support this: **model and prompt-builder are the
two dials; the frozen vector set and the grader stay constant** so every iteration is comparable.

**Non-goals.**
- Not testing blunder *detection*. The records *are* blunders; `tag`/`direction`/outcomes stay in
  the vector (they are part of the genuine production context). The task is to **explain**, and
  grading targets the **mechanism/grounding** the tag does *not* spoon-feed (§5).
- Not replacing `run_eval` / `judge-deep-reveals`. Those remain the **production** evaluator. This
  is a separate, exploratory harness with a different input, model, output, and grader.

## 3. Architecture / data flow

```
 run_eval.mjs --no-llm
   └─► frozen stratified jsonl: one record per case, carrying
         feature_vector  (the model's ONLY input, with glossary)
         + solver ground truth (premove/played/best scores, correct_move)  ← grader-only
                       │
                       ▼
 NEW SCRIPT  server/scripts/explain_from_vector.mjs   (OpenAI, isolated API call)
   for each record, N times:
     prompt = buildPrompt(glossary_file, record.feature_vector)   ← swappable procedure
     answer = call EXPLAIN_MODEL (OpenAI, e.g. gpt-5.4)            ← swappable model
   └─► answers jsonl: { id, run_index, <structured answer §4> }
                       │
                       ▼
 GRADER SKILL  (Claude Code, tools ALLOWED — runs on the Max plan)
   reads answers jsonl + the FULL run_eval records (ground truth) + board tools + solver
   grades each answer on the axes (§5); objective axes by solver/code, mechanism/fabrication by
   board verification
   └─► report: per-case verdict + aggregate + COUNTEREXAMPLE LIST attributed to field gaps
```

**Key seams / invariants:**
- **`run_eval --no-llm` is the data generator** (the `--no-llm` flag already emits records whose
  `feature_vector` is exactly this experiment's input — no duplicate vector generation).
- **The vector set is frozen.** Generate once; iterate (prompt × model) against the same inputs so
  results are comparable across iterations.
- **The script is isolated.** Its prompt contains **only** the glossary text + the
  `feature_vector` JSON + the task. It uses **no tools** and does **not** see solver ground truth.
  (The `feature_vector` legitimately contains `movestring`; that is part of the context.)
- **The grader is privileged.** It has everything the model lacked — solver, `visualize_board.sh`,
  the board, and the record's ground-truth fields — and acts as the **oracle**.
- **Glossary is loaded from the file** (`docs/architecture/feature-vector-glossary.md`) so edits
  are picked up without code changes.

## 4. Structured answer schema (the grader's contract)

The script instructs the model to return JSON (not free prose), so the grader can check it
field-by-field:

```jsonc
{
  "better_move":     "<display column 1-7 or 0-indexed; pick one convention and state it>",
  "played_outcome":  "win | draw | loss",   // with best play
  "best_outcome":    "win | draw | loss",
  "mechanism":       "<why the played move is worse — the load-bearing reason>",
  "key_cells":       ["c5r4", ...],          // squares the mechanism rests on (cNrM, 1-indexed)
  "fields_relied_on":["lookahead.oppCategoryExamples", "threatStats.best.opponentMajorParityAligned", ...],
  "unsure_about":    "<what the vector did NOT let you determine, or empty>",
  "confidence":      "high | medium | low"
}
```

- `fields_relied_on` is the **confound check**: it reveals whether claims trace to engineered
  fields or to the model re-deriving from `movestring` (matters for transfer to the weak model).
- `unsure_about` is the **abstention channel**: an honest "couldn't tell" is **not** a fabrication
  — it is a **feature-gap signal**, and must be graded differently from a wrong claim.

## 5. Grading axes and pass rule

Grade against the oracle (solver + board + record ground truth). The vector already contains
`bestCol`, `tag`, and the outcome labels, so axes A1–A2 are **sanity checks** (a miss there means
the model could not even *read* the vector → a glossary problem). The **substance is A3–A4**.

| Axis | What | How graded | Weight |
|---|---|---|---|
| **A1 better move** | `better_move` == `correct_move` | code (record field) | sanity |
| **A2 outcomes** | `played_outcome`/`best_outcome` match the vector's `*_with_best_play` (and solver) | code/solver | sanity |
| **A3 mechanism is real & load-bearing** | the named tactic/threat/line and `key_cells` actually exist on the relevant board, **and** are the decisive reason (not a true-but-peripheral one) | board + solver verification | **high** |
| **A4 no fabrication** | every concrete claim (cells, threats, lines) is true on the board | board verification | **high (zero tolerance)** |

- **Abstention:** `unsure_about` content is excluded from A4 (not a fabrication) and logged as a
  candidate field gap.
- **Pass rule:** a case **passes** iff A1–A4 hold **on all N runs** (§6). Intermittent success =
  fail — it exposes latent ambiguity in the context.

## 6. Set, repetition, and ablation

- **Stratified set (coverage):** sample from `eval_set_large_*` so the set spans every **kind** of
  blunder — each `tag`, each `direction` (`missed_own`/`defensive_miss`/`enabled_opponent`), each
  `lookahead.case`, sparse vs dense boards, and each outcome flip (win→draw, draw→loss, win→loss).
  A glossary that nails `forced_block` may fail on `claimeven`; coverage is what licenses any
  "~100%" claim.
- **Repetition (stability):** run each case **N ≥ 3** times (same context) to measure variance.
- **Ablation conditions (diagnostics, optional):** to interpret results and check transfer to the
  weak model —
  - **A — full** (glossary + full vector): the headline, production-faithful condition.
  - **B — board-only** (glossary + `movestring`, engineered fields stripped): if B ≈ A, the
    engineered fields add nothing for a capable model; the board carries it (won't transfer to the
    weak model).
  - **C — features-without-movestring**: tests whether the distilled fields alone carry the
    reasoning.
  - **D — grounded render** (added 2026-07-02): the staged, board-anchored prompt that replaces the
    glossary+JSON dump — pre-rendered boards + threat lists + causal-frame text, built by
    `renderReasonModel.mjs` instead of `buildPromptForCondition`'s A/B/C path. Motivated by this
    experiment's A3/A4 failures (deep cells presented as near-term; terse codes narrated as false
    causality). Design + phasing: `reason-render-grounded-prompt.md`. Phase 1 (foundation) shipped;
    the rich causal frames that actually fix the failures land in Phase 3.

## 7. Success criteria & output

- **Success = near-100% pass on Condition A across the stratified set**, all N runs. The number is
  not the deliverable — the **counterexample list is**: each failure attributed to a
  *missing/ambiguous feature field* or a *glossary ambiguity*, with the model's `unsure_about` and
  the grader's board finding. That list drives the next vector/glossary improvement.
- Diagnostic read-outs: per-axis failure breakdown; A vs B vs C deltas; `fields_relied_on`
  distribution (are the engineered fields actually load-bearing?).

## 7b. Adding a new reason case or evidence field — the eval + grader obligation

Owner requirement (2026-07-04): *"adding cases to the reason engine has to also make `select_boards`
cover those conditions... and the grader skill must be aware."* A new case, evidence field, or
predicate in the blunder-reason engine (`computeReason` / `reason_engine/`) is **not complete** when
the engine emits it. Treat **engine field → `select_boards` predicate → glossary → grader skill** as
one atomic unit of work in the plan.

1. **Add the predicate derivation case in `select_boards.mjs`** — in the reason-vector
   predicate-derivation block (near where it does `preds.add('phase_' + r.boardState)`), map the new
   vector field to a predicate name, and **register that name in `REASON_UNIVERSE`**, partitioned
   REQUIRED vs PROVISIONAL. The names must round-trip, or the coverage strategy's
   "emitted-but-unlisted predicate = bug" self-check fires. Skip this and the new case is **never
   harvested**, so it is never evaluated.
2. **Update `.claude/skills/grade-fv-sufficiency/SKILL.md` and `feature-vector-glossary.md`** so the
   grader knows the new field: how to verify its claim against the board, and how to attribute a
   failure (`vector_error` vs `missing_info`). Skip this and the grader mis-scores the new case —
   typically by blaming an existing field for the new one's gap.

A reason field that is in neither the coverage universe nor the glossary/grader is invisible to the
whole eval loop. See `api-conventions.md` §Admin Blunder-Reason Browser Endpoints and memory
`project_reason_render_layer`.

## 8. Reuse / do-not-reuse

  `server/llmCoachHelpers.js` (`callLLM`, env-driven model), the eval sets, `visualize_board.sh`,

- **Do NOT reuse:** the production prompt, zone aliases, `allowedSet`, the annotation gate, or the

  explanation against the board.

### `feature_vector` content traps the glossary does not warn about

Each of these bites any consumer that reads the vector to reconstruct ground truth.

1. **`lookahead.bestOutcome` / `postBlunderOutcome` are `null` for the whole `losing_either_way`
   class** (both moves lose) — not `"loss_with_best_play"`. Any check that maps the vector's outcome
   labels (e.g. the grader's A2 axis) MUST fall back to the solver: `best_scores`/`played_scores` are
   opponent-perspective *after* the move, so the moving player's outcome is the sign of
   `-(max opponent legal score)` (>0 win, =0 draw, <0 loss). Verified on eval-8/12/42/56.
2. **`patternsOpponent`'s board snapshot is unstated and can contradict the after-played board.** On
   eval-51 the vector listed `immediate_threat: {cells:["c5r5"]}` and a `j_shape` while
   `visualize_board.sh` on the after-played board (`43333451540`) shows "Major threats: none" and
   `patternsPostBlunder` is `{}`. A reader naturally places the field on the after-played board and
   produces a claim the board contradicts — so this drives **A4 failures that look like fabrication but
   are a context blindspot**, exactly the counterexample class this experiment exists to surface.
3. **`lookahead.outcomeTiming.*.pliesToEnd` is inverted.** `toPliesToEnd`
   (`server/sparseLookahead.js:25-27`) returns `Math.abs(score)`, and per the c4solver score semantics a
   *small* `|score|` resolves LATE while a large one resolves SOON — the opposite of a forward
   "plies from now" count. `played.pliesToEnd:1` on eval-6 is a ~22-ply zugzwang loss, and the strong
   floor model read it as "loses at once" and fabricated. **Still true in code** (re-verified
   2026-08-28); the glossary was corrected 2026-06-28 to flag it. Never treat it as "moves from now";
   the proposed fix is `endMove(score) - movestring.length`.
4. **`immediate_threat` severity is stamped from the tag name, not verified.** `patternSeverity`
   (`server/explainContext.js`) returns `'immediate'` for any `immediate_threat`/`double_threat` tag
   unconditionally, and `classifyPattern` can emit `immediate_threat` on a cell that completes no
   4-in-a-row (eval-6: `c3r2`, simultaneously in `opponentMinor`, only draws). Gate
   `severity:'immediate'` on a real win-completion check (`checkWin` at the gravity-top cell) before
   trusting the field as a decisive threat.

**Cross-cutting principle from the v2 run: a confidently-wrong field is worse than an absent one.**
Condition B (fields stripped) abstains; conditions A/C with misleading fields fabricate at high
confidence. Prune and verify aggressively — absence is safer than a plausible-but-wrong value.

## 12. WHICH STRING the harness records, and which one each axis grades (2026-08-26)

The single most misread property of this experiment. `answer.mechanism` in an
`fv_suff_answers_*.jsonl` row exists at three layers, and a count is meaningless without naming one.

| layer | how to obtain it | what it is |
|---|---|---|
| **raw** | `answer.mechanism` as stored | post-`processAnnotations` (`compute.mjs`'s `postprocessAnswer`), **pre-guard**; still carries `[zone:…]`/`[term:…]` markup. **This is NOT what a player receives.** |
| **prose** | raw, minus `/\[\/?(zone\|term):[^\]]*\]/g` | the layer the coach-voice axis actually grades — the rubric orders markup stripped before grading |
| **served** | raw, through `guardExplainMoveLlmPayload` (`server/reasonRenderGuard.mjs`) with a real `board` + `allowedSet` | what `GET /api/user/blunder/:id/deep-reveal` returns |

**As built, the harness records the RAW layer and the agent-graded judgment axes grade it.** That is a
known instrument defect, not a design choice: production runs a three-stage guard
(`humanizeGroundedCoordinates` → `promoteRawCoordinates` → `stripInternalTokens`) over the string
before serving, so those axes charge text no player ever sees. Measured 2026-08-26 on the 25-board
subset: raw internal `cNrM` coordinates appear in 120 of 125 raw strings, 62 of 125 at the prose layer,
and **0 of 125 at the served layer**. Moving the judgment axes to the served string is Epic 12 / US1
(`docs/epics/deep-reveal-remediation-epic.md`).

**One axis is already post-guard.** `grade_mechanical.mjs`'s A6 imports production's

## 13. `toFeatureVector` field-selection rule

The owner's standing rule for what belongs in a vector read by a thinking model. The bar for removal is
**plumbing / derivation / search artifact** — never "it's verbose".

**KEEP — grounded board detail.** Cells are first-class signal: they complement the movestring with
specifics not recoverable from counts. This covers the static `classifyPattern` maps
(`patternsBest`/`Played`/`PostBlunder`/`Opponent`, tag→{cells}), parity-bucket threats **with cells**
(`threatStats.{pre,best,played}`, each bucket `{count, cells}`), `playedCell`/`bestCell`,
`centerDominance` (the sole signal on opening boards), and the look-ahead's novel cell-sets
(`categoryExamples`/`oppCategoryExamples`). **Over-pruning trap:** cells, the pattern maps and
`centerDominance` were each dropped once and had to be restored. Do not flatten grounded cells to counts.

**DROP — LLM-prompt plumbing.** `allowedSet` (the P5strong validation whitelist — explicitly not a
tactical feature, however data-rich it looks), `zoneAliasMap`, all reason prose
(`humanReason`/`positiveReason`/`terseReason`), KB-term plumbing
(`relevantPatternKeys`/`kbTerms`), display labels (`playerName`), the rendered
`threatComparison`/`threatShowFlags`, and the redundant `lookaheadRaw`.

**DROP — pure derivations and noisy search artifacts.** Derivations: `opponentPerspective`, `isOptimal`,
`gapBucket`, `positionTier`, `lookaheadFired`. Search-artifact magnitudes: raw `occurrences` are DFS
detection-node counts that scale with depth/budget/branching, so their magnitudes mislead a model into
over-weighting and naive subtraction. Keep only board-bounded **instance** counts: `novelInstances`
(distinct novel cells — a set difference, which a model *will* conflate with the occurrence delta) and
`perCategory`'s `bestInstances`/`playedInstances`.

**Tactical-only invariant.** A field may be *computed* from the solver, but what it *surfaces* must read
tactically — threats, columns, parity, named patterns, "wins/loses in N moves" — never solver internals
(scores, raw `|score|` magnitudes). This is why `pliesToEnd = Math.abs(score)` is a bug rather than a
naming issue: it leaks a score magnitude with inverted meaning.

**Scope note.** The production coach prompt does not see any of these counts (it gets the winner's cells
via zone tags plus the pattern name), so trimming the vector cannot break the live coach.
`toFeatureVector` defaults `prune:true` (recursive empty/all-zero elimination), but `buildExplainContext`
overrides to `prune:false` so the wire carries the full fixed shape and the admin tool can toggle
collapse both ways.

## 14. Reproducing one case, and verifying a cell

**Reproducing.** Boards and evidence live at the stable path
`connect-four/server/scripts/reason_corpus/` (`boards.jsonl` + `evidence.jsonl`, same ids in the same
order; the older `fv_suff/boards_coverage_*.jsonl` soup is deleted). **`id` is not a positional index** —
the 50 harvest rows keep `eval-N` ids, but the 13 regression rows carry *semantic* `pin-*` ids
(`pin-L5-deep-fork`, …). Look a row up **by id, never by line number**, and extract the real row rather
than hand-constructing one, so the row's `selection.predicates` provenance matches the run you are
reproducing. The glossary is read fresh at prompt-build time, so a glossary edit takes effect without
regenerating evidence.

To actually reproduce a single case, extract that one row by id (grep by `"id":"pin-…"` or by
`movestring` — never by line number, since ids are not positional) into a one-row file, then run
`compute.mjs --input one.jsonl --out one_out.jsonl --llm`.

**Verifying a cell / window / line.** Compare it against the engine's **own** `finalMovestring`/`line`,
not an independently traced solver principal variation. Connect Four positions have many equally-optimal
winning lines, so a cell absent from *your* PV can be entirely real on the engine's. In the 2026-07-02
Phase-1 grading run this bit 3 of 4 "failures" — eval-1 (mis-triaged `vector_error`), eval-16
(mis-triaged as A4 fabrication) and eval-3 were all correct deep fields wrongly convicted because the
grader compared against a different optimal PV; replaying the engine's `finalMovestring` flipped eval-1
and eval-16 to pass. Before ruling a deep field wrong, replay that half's `finalMovestring` and confirm
whether the named window completes there. "Not visible on the board now" **and** "not in my PV" are both
invalid grounds to convict.
