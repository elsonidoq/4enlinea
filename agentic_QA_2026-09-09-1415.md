### Area: Lessons — Board win-overlay ring color (OI-168 regression in the fix itself)

#### [major] The `win` overlay ring is STILL hardcoded green in the rendered page — the CSS `pulse` keyframe overrides Board.jsx's color-aware inline style, so the ring/legend now visibly disagree

- **Severity:** major
- **Area:** Board win overlay — `src/components/Board.jsx` win-ring rendering + `src/styles/tokens.css` `@keyframes pulse`
- **Suspected code location:** `src/styles/tokens.css:84-87` — `@keyframes pulse { 0%,100% { box-shadow: 0 0 0 3px rgba(43,180,98,.9); } 50% { box-shadow: 0 0 0 6px rgba(43,180,98,.25); } }`. `Board.jsx:362-369` sets the *inline* `boxShadow` color-aware (`value === 'yellow' ? var(--disc-gray-hi) : var(--eval-good)`) per the OI-168 fix, then applies `animation: 'pulse 1.4s infinite'` on the same element. A CSS animation's `box-shadow` keyframe values win over the element's own inline `style.boxShadow` for the whole animation cycle (0% is still an animated frame, not "no animation yet") — so the keyframe's hardcoded `rgba(43,180,98,...)` (green) always wins, on every win-ring, regardless of which color the inline style computed.
- **Repro steps:** 1. Sign in, tier free. 2. `/concept/block-before-build` slide 1/4 ("Gray's three in a row"). 3. Read the DOM: the legend swatch for "Gray's three in a row" and the ring color drawn on the 3 board cells it labels (col 2/3/4, row 1 0-indexed — all GRAY discs per `boardSpecToBoard`).
- **Input used:** lesson `block-before-build`, slide index 0, tier free, default desktop viewport.
- **Observed:** legend swatch computed `background: rgb(82, 90, 107)` (correct gray, matches `--disc-gray-hi`) — the OI-168-E2 legend fix works. But the three win-ring `<span>`s on the board compute `boxShadow` containing `rgba(43, 180, 98, ...)` (green, `--eval-good`), on GRAY discs. Screenshot: `qa-evidence-oi168-green-ring-on-gray.png` (repo root of this worktree).
- **Expected:** ring color should match the legend and the disc's own color — gray ring on gray discs, per the OI-168 fix's stated intent (`Board.jsx`'s own comment: "the ring takes the identity of the disc it rings, so marking GRAY's connected discs no longer draws a GREEN ring on them (OI-168)").
- **Root cause:** confirmed at source — `src/styles/tokens.css:84-87`'s `@keyframes pulse` hardcodes the ring color to `rgba(43,180,98,*)` in BOTH its 0%/100% and 50% frames. Any element animated with `animation: pulse ...` has its `box-shadow` driven entirely by the keyframe for the animation's whole duration; the element's own inline `boxShadow` (the color-aware value Board.jsx computes) is only what would show if the animation were removed/paused — it never paints. The Board.jsx code-level fix and the DOM-level legend fix are both correct; the shared `pulse` keyframe is the one place still hardcoded, and it silently wins over both. **This means OI-168's board-ring half is still broken in the actual rendered app** despite the unit-tested token-string assertions in `winLegendSwatch.test.js`/`BoardWinOverlayColor.dom.test.jsx` passing — those tests assert on the computed inline `style.boxShadow` string (per the remediation ledger's own disclosed limitation: "jsdom paints nothing... every assertion is on the TOKEN STRING"), which is exactly the layer this bug hides behind — jsdom never runs the CSS animation, so the test's assertion on the inline style never sees the keyframe override a real browser applies.
- **If picked up:** parameterize `pulse`'s ring color (e.g. two keyframes `pulse-green`/`pulse-gray`, or animate a CSS custom property and reference `var(--win-ring-color)` inside the keyframe, set inline per-cell) so the animation stops overriding the color-aware inline style.
