## Settled Decisions (non-negotiable — reflect verbatim, do not re-derive or relitigate)

These were resolved by the project owner before this spec was written. An implementation that contradicts any of them is a defect, not a design choice to revisit.

1. **`agentic_QA_2026-07-15-1321.md` at the repo root is the authoritative work-list for OI-35** — this spec is a pointer, not a re-listing. It is confirmed present (83,360 bytes) but **untracked**: `git status --short` reports `?? agentic_QA_2026-07-15-1321.md` and `git log --diff-filter=A -- agentic_QA_2026-07-15-1321.md` returns empty — no commit on any branch has ever added it. US1 must (a) commit the file so the work-list stops being a single-machine artifact, and (b) write the durable triage result into `docs/open_issues.md` under OI-35 — updating the findings file in place is not sufficient on its own.
2. **Do not fold game outcome into the accuracy calculation** (OI-37). It measures board-move optimality and is correct on its own terms; conflating it with "did you finish the game" destroys both answers. This is a **scoped finding, not a full correction**: in the 342-game Papergames import measured during the epic's brainstorm (see Non-Obvious Facts), every accuracy-100% loss is a `time-up` (clock) loss and real `resignation` losses top out at 89%. That is a statement about one imported dataset, not a general refutation of the epic's original "resigns after playing perfectly" framing — the findings file (`agentic_QA_2026-07-15-1321.md`, Batch A, "[minor] Lost games report 'No mistakes' / 100% accuracy") contains an explicit **in-app** repro of the resignation case that the Papergames import did not exercise, and the in-app resign path remains unmeasured until US3 measures it. The rationale for leaving the accuracy calculation untouched holds regardless of which trigger produces the badge. The copy fix (`review.cleanButLost`) already shipped; what remains is reproducing the in-app repro (US3's first accuracy-half task, before any close-as-not-a-bug claim) and then closing OI-37 with evidence covering **both** triggers.
3. **OI-21: accept first-interaction playback (status quo).** No new splash screen, no welcome card, no routing change, no speaker affordance. The greeting plays on whatever the user first touches; the epic's own acceptance criterion already permits this ("... or the accepted alternative is documented"). What remains is documenting the alternative and its rationale, verifying the coach's **text bubble** fully conveys the greeting in English and Spanish (so a user who never hears the audio loses nothing), signing off the `staging_checks.md` item, and closing OI-21. `shouldAutoRouteToOnboarding`'s anonymous-only semantics and the no-flash-of-the-sparring-game constraint still apply and are not being touched.
4. **OI-37 short-game half: a minimum-scored-moves threshold was considered and rejected.** All 7 observed accuracy-100% losses are very short, 1–6 user-move `time-up` (clock) losses (movestring lengths 2, 5, 5, 8, 11, 13, 13), and a threshold of 7 user moves would have suppressed the badge on all 7 of them at a cost of 48/342 games (14.0%, see Non-Obvious Facts for the full trade-off table). The owner rejected building it, in these words: *"Forget about the short game threshold. Do nothing special to those games. There are more risks of introducing a new issue than anything else."* The change would touch multiple render surfaces (in-app Review, Past Games, and — if a Papergames derivation were added — the imported-game badge) for a narrow cosmetic case, and carries more regression risk than the problem is worth. **Nothing is shipped for the short-game half.** The measured trade-off data is kept for the record only, not as a spec-phase pick, and no threshold, suppression rule, or new Stats metric may be added on any surface as a result of this spec.
5. **US3's deep-reveal spend policy is already decided — record-and-close, ship no gate.** Approved 2026-07-16 (`docs/superpowers/specs/2026-07-16-qa-remediation-decisions-design.md` §D2): retire the "blunders only" constraint from the anon design doc, ship no code. A server-side gate isn't cleanly implementable (the anon gate is keyed by position+column, which maps ambiguously to stored rows); a client-only gate is theatre (`/api/blunders/:id` is a public no-auth permalink); and blocking a click the user deliberately made costs conversion. This also avoids contradicting shipped spec-042's invariant that severity is "label + color only, never gates an action." The "anon design doc" carrying the stale "blunders only" line is `docs/superpowers/specs/2026-07-13-anon-free-deep-reveal-design.md:41`, still live. A second, distinct document — `docs/superpowers/plans/2026-07-13-anon-free-deep-reveal.md:18` — already carries the equivalent line struck through and marked `RETIRED 2026-07-16`; it is evidence D2 shipped, not a target for editing. Because `docs/superpowers/` is throwaway by repo convention, D2's substance is restated here (and must land in **both** `docs/open_issues.md` **and** `docs/epics/open-issues-epics.md`), not left as a pointer to a throwaway doc.

  | threshold (user moves) | games whose badge is suppressed | of the 7 perfect losses caught |

  | 4 | 22 / 342 (6.4%) | 3 / 7 |

  | 6 | 32 / 342 (9.4%) | 5 / 7 |
  | 7 | 48 / 342 (14.0%) | 7 / 7 |

### User Story 2 - Document the accepted onboarding alternative (Priority: P2)

The coach's onboarding greeting cannot play the instant the mission screen appears on a cold load, because browsers block audio playback before any user gesture has occurred, and the mission screen is reached by an automatic route with no gesture yet made. This has already been decided as acceptable: the app keeps its current behavior (the greeting plays on the user's first tap/click/keypress instead of instantly), and no new onboarding UI is introduced to force an earlier gesture. What remains is making sure a user who never hears the audio still gets the full greeting from the on-screen text, recording the decision, and — because this decision has never actually been confirmed against a real browser's autoplay policy — obtaining that confirmation before signing off `staging_checks.md:495`, whose own text warns "if it's silently blocked, that's a bug to file, not a pass."

**Why this priority**: This is a small, decided, record-and-close story for the design question itself — but it carries the spec's one manual, non-automatable verification step (a real-browser audibility check), so it is not pure documentation.

**Independent Test**: With the app's audio muted (or in a state where autoplay is blocked), reach the onboarding mission screen in both English and Spanish and confirm the coach's on-screen text bubble alone conveys the full greeting content, without needing to hear it. **Acceptance Scenarios**:

1. **Given** a first-time anonymous user reaches the onboarding mission screen on a cold load, **When** they never interact with the page before reading the coach's bubble, **Then** the visible text alone fully conveys the greeting in both English and Spanish.

### Edge Cases

- What happens if a finding in the QA backlog was already independently fixed by unrelated work landing on the tree between the QA run and this spec's implementation? It gets the "fixed" disposition with the specific evidence (file/line, test, or commit) that shows it — not silently dropped and not re-fixed.
- What happens if the `/mistakes ↔ /stats` cold-load nav loop no longer reproduces when live-checked? It is recorded as "stale" or "fixed" with evidence of the live check, and no code changes are made for it — reproducing a fix that already shipped elsewhere is not a goal of this story.
- What happens if a QA finding's fix would require touching a file/module owned by a different, currently-running parallel epic? It is recorded as an owned-by-that-epic pointer only; this spec does not edit that file.
- What happens if `docs/superpowers/specs/2026-07-13-anon-free-deep-reveal-design.md:41`'s "blunders only" line is already gone by the time this ships (distinct from `docs/superpowers/plans/2026-07-13-anon-free-deep-reveal.md:18`, which is confirmed already retired and is not this scenario's subject)? It is **not** a trivial pass: confirm the reversal-trigger note is present at that path and add it if missing — the retirement of the *other* document does not substitute for this one.
- What happens if the in-app resign repro reveals a DIFFERENT symptom than the original finding described (e.g. a different message, or a partial fix already landed)? The actual current behavior is recorded as the evidence, and OI-37 is closed (or kept open with a dated update) based on what is actually observed, not on the original finding's exact wording.
- What happens to a user who has JavaScript audio blocked entirely (not just autoplay-blocked, but permanently muted or using an assistive device)? The text-bubble-only guarantee in US2 already covers this — nothing in this spec depends on the user ever hearing audio.
- What happens if a genuinely-earned high accuracy score at a longer game length (e.g. 13+ user moves) is observed during this story's work? It must not be affected by anything shipped here — no threshold exists to suppress it, by design.

### Key Entities

- **QA finding**: A single reported item from `agentic_QA_2026-07-15-1321.md` (severity, code location, repro steps), each assigned exactly one of the five dispositions defined in FR-002.

- **Deep-reveal spend**: An anonymous user's single free use of the deep-reveal explanation feature; this feature records that its eligible-move-type policy stays unrestricted.
