# Feature Specification: Detector Perspective Soundness & Blunder Tag Taxonomy

**Feature Branch**: `052-detector-perspective-taxonomy`
**Created**: 2026-07-30
**Status**: Draft
**Input**: User description: "Epic 2 — Detector Perspective Soundness & Blunder Tag Taxonomy" (`docs/epics/open-issues-epics.md`, section "## Epic 2"). Finish the OI-74 perspective-soundness cleanup for the remaining detector (`detectOvercut`) and stop the blunder vocabulary from mislabelling what the player actually did. Blunder tags are stored, user-visible content, so every detector change is a content migration, not just a code change.

## Context this spec inherits (do not re-derive)

This epic is the direct sequel to OI-74, already resolved (`docs/open_issues.md`, "OI-74 — `detectUndercut`'s `perspective` parameter is unsound … **Status**: ✅ RESOLVED 2026-07-28"), which split `detectUndercut` into `detectUndercutVictim` / `detectUndercutBeneficiary` and documented the resolution in `docs/architecture/server-conventions.md` §"Undercut has two sides". Epic 2 applies the same treatment to `detectOvercut` and separately fixes the `drawing_move` mislabel and two creation-gate residuals.

Verified at source (`connect-four/server/classifier.js:1020-1073`), current `detectOvercut`:

```js
export function detectOvercut(board, scores, perspective = board.currentPlayer) {
  // @see allen-t4, allen-t5, allen-t2
  const threats    = board.reachableThreats(perspective);
  const oppThreats = board.reachableThreats(3 - perspective);
  ...
  for (let col = 0; col < COLS; col++) {
    if (board.colHeights[col] >= ROWS) continue;
    if (!scores || scores[col] <= 0) continue; // overcut requires playing C to be winning
    const colRows    = threats.get(col) ?? [];
    const oppColRows = oppThreats.get(col) ?? [];
    for (const R of colRows) {
      const neutralised = oppColRows.find(rp => rp < R);
      if (neutralised === undefined) continue;
      if (!isT4SameParity(R, neutralised) &&
          !isT5Exception(R, neutralised) &&
          !isT2Blocking(colRows, neutralised)) continue;
      ...
      matches.push({
        col,
        reason: isT4SameParity(R, neutralised) ? 'same_parity_t4'
              : isT5Exception(R, neutralised) ? 'active_forcing'
              : 'chain_t2',
        ...
      });
```

`threats` follows the caller-supplied `perspective`, but `scores` are always the side-to-move's (c4solver convention — see `docs/architecture/reason-INVARIANTS.md` I10: "Solver score is from the side-to-move"). When `detectOvercut` is called with `perspective !== board.currentPlayer`, it mixes one player's threats with the other player's score sign — the exact defect OI-74 already removed from undercut. This is not hypothetical: `tagBlunder`'s Phase C (`classifier.js:1961`, `MISSED_OWN_PRIORITY`) evaluates `overcut` on `moves + correctCol` where the tagged player is **not** the mover, i.e. production always takes the unsound branch today. Fixing the detector therefore changes stored, user-visible blunder tags.

Two things this spec must NOT re-do (already shipped in this worktree, spec 051 T015, verified at `classifier.js:1025-1073`): `detectOvercut` already accumulates every matching column into a `matches` array instead of returning on the first hit. Set-valued acceptance is a precondition, not a task here.

Two things this spec must NOT touch: `detectFigure7` / `detectJShape` — their second parameter is `_scores`, genuinely unused; they are pure kernel convolutions over `perspective`'s own discs and are sound for any perspective (an earlier draft of OI-76 got this wrong by argument shape; see `docs/open_issues.md` OI-76: "**Not affected — do not \"fix\" these**").

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A player's stored blunder tag correctly names who did what (Priority: P1)

A player who blunders an overcut opportunity — either giving up their own winning overcut, or letting the opponent's overcut stand — sees/receives a blunder tag and highlighted cells that describe the pattern from the mover's own perspective, matching what actually happened on the board. Today the tag can be computed from the *wrong* player's threats crossed with the *mover's* score sign, producing a description that does not match the board.

**Why this priority**: This is the actively-shipping defect (OI-76). Every `overcut` blunder tag currently stored or generated by `tagBlunder`'s `MISSED_OWN_PRIORITY` phase is computed on the unsound branch. Every other story in this epic either depends on this fix (US2.2 extends the same detector) or is independent of it, so it must land first.

**Independent Test**: Can be fully tested by re-running `tests/blunder/tagBlunderFixtures.test.js` against a fixed `detectOvercut` (or its role-named replacements) and confirming every `overcut`-tagged fixture's cells/columns match a board where the tagged player, not some other player, actually holds the described threat.

**Acceptance Scenarios**:

1. **Given** a board where the side to move owns a major threat that is not neutralized by the opponent's lower threat in the same column (an overcut win for the mover), **When** the detector evaluates that position, **Then** it reports the mover as the beneficiary using only the mover's own threats and the mover's own (side-to-move) score.
2. **Given** a board where the side to move's major threat in a column is legitimately dead (T2 applies, no T4/T5/chain exception), **When** the detector evaluates that position, **Then** it does not report an overcut match for that column.
3. **Given** the existing `tagBlunder` `MISSED_OWN_PRIORITY` phase evaluates a real blunder board where the blunderer is not the mover of the position being scored, **When** the fixed detector runs, **Then** the resulting tag's cells describe threats that genuinely belong to the tagged player, and any fixture whose expected output changes is reviewed and explicitly approved (not silently regenerated) before being committed.
4. **Given** the local puzzle/candidate pool, **When** the count of active `overcut` rows is re-measured against the current database (not assumed from the 2026-07-29 measurement of zero), **Then** the spec's implementation records the current count and, if non-zero, re-derives `highlight_metadata` for those rows and reports whether the pool needs repair.

### User Story 2 - "Active forcing" overcut is recognized as a first-class blunder pattern (Priority: P2)

The overcut lesson (`lesson-12-overcut.json`) teaches a gravity-top-adjacent shape — the opponent's threat sits directly beneath the mover's, is odd-column-parity, and the mover's play blocks it while immediately threatening from above. Today's detector never matches this shape as its own case; a board exhibiting it either falls through to a different (mislabeled) match or is missed entirely, and the existing `'active_forcing'` label is in fact attached to an unrelated branch (the T5 rows-3/6 exception).

**Why this priority**: Depends on User Story 1's perspective fix being in place first (both stories touch the same detector), and is a content-completeness gap (OI-60) rather than a soundness defect, so it follows the correctness fix.

**Independent Test**: Can be fully tested by constructing a board matching the community-overcut KB's "active-forcing" sub-case (case (e): current player plays an odd-empty-count column first, blocking the opponent's lower threat and creating an immediate check at R) and confirming the detector reports a match for it, distinct from the T5-exception case.

**Acceptance Scenarios**:

1. **Given** a board where the mover's major threat is directly above the opponent's threat in the same column, the column has an odd number of empty cells, and it is the mover's turn, **When** the detector evaluates that column, **Then** it reports a match tagged with a name that is decided and recorded (see Open Questions) — not silently reusing whichever existing label was already assigned to a different branch.
2. **Given** the T5 rows-3/6 exception case (rows 3 and 6 in the same column, opposite parity, non-interacting per Allen T5), **When** the detector evaluates that column, **Then** it is still reported, under whichever label the recorded decision assigns to it, distinguishable from the new active-forcing branch.
3. **Given** the four documented mechanisms that prevent T2 from neutralizing an upper threat (minor-threat exception, same-parity/T4, T5's row-3/6 exception, chain-T2, and now active-forcing), **When** each is exercised by its own counterexample board, **Then** each produces the correct, distinct match — no single board is used to validate more than one case.
4. **Given** the taxonomy decision from Acceptance Scenario 1 is made, **When** implementation completes, **Then** it is recorded in the reason-engine decision log with rationale, lesson 12's copy and any deep-reveal shape naming referencing the old label are updated to match, and `docs/knowledge-base/community-overcut.md`, `allen-t2.md`, `allen-t4.md`, and `allen-t5.md` gain cross-references reflecting the shipped `detectOvercutVictim`/`detectOvercutBeneficiary` split and the new active-forcing branch.

### User Story 3 - A forfeited forced win is never described as merely "a draw" (Priority: P2)

A player who had a forced win available and instead played a move that only draws currently receives the same blunder tag (`drawing_move`) as a player who genuinely had no better option than a draw. The two situations are not equivalent in severity or lesson value, and the current tag conflates them in both the live sparring coach and the stored/reviewed blunder pipeline.

**Why this priority**: Independent of the overcut work (different detector/tag entirely), but it is a real, currently-shipping mislabeling defect (OI-48) affecting player-visible feedback in two separate code paths, so it carries equal priority to fixing the overcut defect.

**Independent Test**: Can be fully tested by constructing a near-empty-board position where the center column is a forced win and a side column only draws, playing the drawing column through both the live sparring endpoint and the stored blunder-tagging pipeline, and confirming neither path emits the same tag/label it would emit for a position where the best available outcome was genuinely a draw.

**Acceptance Scenarios**:

1. **Given** a position where the best move wins and the played move only draws, **When** the live sparring coach classifies the move, **Then** the resulting tag distinguishes "you forfeited a win" from "the best available outcome was a draw."
2. **Given** the same distinction, **When** the stored/reviewed blunder-tagging pipeline (used for the review screen and any persisted blunder analysis) classifies an equivalent position, **Then** it applies the same distinguishing treatment as the live path — fixing one path is not treated as fixing both.
3. **Given** a position where the best move and the played move both only draw (a genuine draw-to-draw case), **When** either path classifies the move, **Then** the tag is unchanged from today's `drawing_move` behavior — the fix narrows the mislabeled case without altering the correct one.
4. **Given** the taxonomy decision (mint a new tag vs. refine the existing tag's sub-reason/direction field — see Open Questions) is made, **When** implementation completes, **Then** every place that stores, validates, displays, or explains the tag (the database constraint, the server-side tag registry, the architecture docs, both locales' display text, the reason/explanation vocabulary, the LLM-context tag list in server code, and the LLM-facing glossary document) is updated consistently, and the decision is justified in writing.
5. **Given** whichever taxonomy decision is implemented, **When** the change is complete, **Then** the downstream grounding-rule text (Fix 4) is re-read against the shipped behavior and confirmed to still read correctly, with any drift corrected.

### User Story 4 - A second, genuinely new tactical fork is recognized as newly created (Priority: P3)

When a player already holds a winning fork and creates a second, distinct fork with their move, the live coach's "you just created this" praise is currently suppressed — because the gate only tracks whether the mover held *a* fork before the move, not *which* columns it occupied. The same imprecision applies to the forced-win creation gate.

**Why this priority**: A known, accepted-but-fixable residual (OI-33) with no production risk today (the player is already being told they're winning) — lower urgency than the two mislabeling defects above. This story is scoped to its own two gates (fork creation, forced-win creation) only; it is not shared infrastructure for User Story 5, which uses the existing absent→present transition gate independently and can ship before, after, or in parallel with this story.

**Independent Test**: Can be fully tested by constructing a board where a mover already holds a fork in one pair of columns and creates a second, distinct fork in a different pair with their move, and confirming the "creation" signal fires for the second fork even though a fork already existed before the move.

**Acceptance Scenarios**:

1. **Given** a mover already holds a fork in columns A and B before their move, **When** their move creates a new, distinct fork in columns C and D, **Then** the creation gate recognizes this as a new creation rather than suppressing it because a fork already existed.
2. **Given** a mover's move does not change which fork columns are live, **When** the gate evaluates the move, **Then** it does not report a new creation (no regression from today's suppression behavior in the non-creation case).
3. **Given** the equivalent imprecision in the forced-win creation gate, **When** the same fix is applied there, **Then** a genuinely new forced-win opportunity is recognized as a creation even if the mover already had a different forced win before the move.
4. **Given** the puzzle-generation pipeline's consumer of this same classification logic (which is not covered by the fast test suite because its test hangs on real solver calls), **When** this story's fix lands, **Then** a new regression exists that exercises that consumer's behavior without invoking the real solver, so a future regression here is caught automatically.

### User Story 5 - The live coach can recognize and praise more tactical patterns during play (Priority: P4)

Currently, if a player builds a figure-7, j-shape, z-threat, undercut, overcut, odd-even-threat, or claimeven pattern during live sparring, the coach never says so — these patterns are only ever recognized in the offline blunder-analysis and puzzle pipeline, never during a live game, even though phrase pools for praising them already exist.

**Why this priority**: This is a net-new feature (not a defect fix), and several of the underlying detectors call the solver, which has a real per-move latency cost during live play — it must be evaluated and possibly limited in scope, making it appropriately the lowest priority in this epic.

**Independent Test**: Can be fully tested by playing a live sparring move that creates one of the chosen patterns for the first time in the game and confirming the coach praises it exactly once (not on every subsequent move where the pattern merely persists), for each pattern chosen for inclusion.

**Acceptance Scenarios**:

1. **Given** a decision is made about which of the multi-tag tactics are worth adding to live play (weighing solver-call latency for each), **When** that decision is implemented, **Then** only the selected patterns are added to the live coach's recognition, and the rationale for inclusion/exclusion of each candidate is recorded.
2. **Given** a pattern is added to live recognition, **When** a player's move causes that pattern to newly appear on the board, **Then** the coach praises it, but if the pattern was already present before the move (mere persistence, not creation), the coach does not re-praise it on every subsequent move.
3. **Given** a pattern is added to live recognition, **When** the coach praises it, **Then** the corresponding phrase pool exists and renders correctly in both supported locales.
4. **Given** each newly-added pattern, **When** it is exercised by a dedicated test, **Then** the test confirms the tag is reachable end-to-end (detection → tag → phrase) for that specific pattern.

### Edge Cases

- What happens when a board exhibits **both** a legitimate overcut match and the new active-forcing match in the same column? (Per the community-overcut KB's known limitation: "the column must have odd parity AND it must be the current player's turn at the moment of evaluation" — the two mechanisms are evaluated as alternative reasons for the same neutralization, not as independently co-occurring matches on one `(col, R, R')` triple; the detector's existing "first qualifying reason wins" precedent should be respected and documented.)
- What happens when the mover's threat and the opponent's threat at the same row are **mutual** (both players have a threat at the same cell, i.e. `[*]` in `visualize_board.sh` notation)? The community-overcut KB's own false-positive example (`10231405030112342031435`) shows the "active forcing" sequence backfiring when the target row is mutually contested — the detector must not match this as a safe overcut.
- What happens to an existing `overcut`-tagged blunder fixture whose only qualifying branch changes from `'active_forcing'` to a renamed label (or vice versa) purely due to the taxonomy relabeling, with no change in which board/column matched? (This must still be surfaced as a diff for human review, per the "read-and-approved fixture diff" requirement — a text-only rename is not exempt from review.)
- What happens on a board where **no** `overcut` match exists at all under the old code, but a match appears under the corrected perspective logic (a false negative fixed, not just a false positive)? The fixture-diff review must cover new matches appearing, not only existing matches changing.
- What happens when a `drawing_move`-tagged position is a genuine draw-to-draw case that was previously miscategorized as a forfeited win by a bug in the classifier, rather than the reverse? The fix must be validated in both directions (I12: a counterexample per case, not just the motivating repro).
- What happens when the second, distinct fork in User Story 4 shares one column with the pre-existing fork (e.g., columns A/B before, C/A after)? The per-column diff must correctly treat this as "one new column, one retained" rather than either "fully new" or "no change."
- What happens when two distinct forced-win lines in User Story 4 share the same anchoring immediate-threat column? This is an accepted, documented limitation of the minimal per-instance identity fix (not solved by this epic) — it MUST be recorded as its own entry in the project's open-issues log rather than left undocumented or silently folded into an existing entry's closeout.
- What happens when a live-praised pattern (User Story 5) requires a solver call and the solver is temporarily unavailable or slow? The live coach path must degrade (skip praising that pattern for the move) rather than blocking or erroring the player's move submission.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The overcut detector MUST determine which player is the "victim" (owns the upper, neutralized-or-not threat) and which is the "beneficiary" (owns the threat that survives/wins) based on who is to move in the position, never from a caller-supplied argument — mirroring the resolution already shipped for undercut (`docs/architecture/server-conventions.md` §"Undercut has two sides": "Which role a player holds is fixed by the position — specifically by **who is to move** — never by a caller-supplied argument"). The detector's threats and its score gate MUST read from the same player.
- **FR-002**: The overcut detector's public interface MUST NOT accept a `perspective` parameter that can diverge from the side to move. `perspective` MUST be dropped from the public interface entirely — exactly as `detectUndercutVictim`/`detectUndercutBeneficiary` already do — per the epic's Settled decision 1. A caller wanting the non-mover's overcut status MUST NOT be served by silently flipping the score sign.
- **FR-003**: The overcut detector MUST be split into two role-named exported functions, `detectOvercutVictim(board, scores)` and `detectOvercutBeneficiary(board, scores)`, mirroring the shipped undercut pair (`classifier.js:981` `detectUndercutVictim(board, scores)`, `:1003` `detectUndercutBeneficiary(board, scores)`) exactly — same parameter shape, same role-resolution-by-side-to-move, no `perspective` parameter on either function. Every call site that previously called `detectOvercut(board, scores, perspective)` MUST be updated to call the role-named function matching the role it needed — specifically, `classifyPattern`'s detector list (the call site reached by `tagBlunder` Phase C's `MISSED_OWN_PRIORITY` evaluation on the already-moved board) MUST call `detectOvercutVictim`, since the side to move on that board is the opponent, not the blunderer; a bare detector-level unit test does not validate this — a **regression at the `tagBlunder`-pipeline level**, asserting the tagged cells belong to the blunderer, MUST also be added for this call site.
- **FR-004**: The system MUST NOT change the signature or scoring behavior of `detectFigure7` or `detectJShape` as part of this work (their unused `_scores` parameter and perspective-agnostic soundness are out of scope and must not be "fixed").
- **FR-005**: Every stored blunder-tag fixture whose expected output changes as a result of the overcut fix MUST be individually reviewed by a human before being committed as the new expected value — a bulk fixture regeneration without review does not satisfy this requirement.
- **FR-006**: Before any `highlight_metadata` re-derivation work for active `overcut` puzzle/candidate rows is performed, the system MUST re-measure the current count of such rows against the live database (local, and staging/production if reachable) rather than relying on the prior (2026-07-29) measurement of zero. If staging or production is unreachable at measurement time, the system MUST record that fact explicitly (not assume the count is zero or unchanged there) and escalate rather than silently proceeding as if only the local count mattered.
- **FR-007**: The overcut detector MUST recognize the gravity-top-adjacent "active forcing" shape described in `docs/knowledge-base/community-overcut.md`'s formal predicate case (e) (odd-empty-count column, mover's turn, mover's threat immediately above the opponent's blocked threat, immediate check created) as a distinct, first-class match, not merely a byproduct of an existing branch.
- **FR-008**: The system MUST record an explicit decision — not a silent default — about whether the label `active_forcing` remains attached to the existing T5 rows-3/6 branch (`classifier.js:1052`'s `isT5Exception` condition) or is reserved for the new KB-matching branch described in FR-007, with the T5 branch renamed if reserved elsewhere. This decision MUST be written into the reason-engine decision log (`docs/architecture/reason-DECISIONS.md`) with its rationale.
- **FR-009**: Each of the documented mechanisms that can produce an overcut match (minor-threat exception, same-parity/T4, T5 rows-3/6 exception, chain-T2, and the new active-forcing branch) MUST be validated against its own dedicated counterexample board exercised through the production detector — no single board or hand-rolled proxy may stand in for more than one case. The minor-threat branch MUST require a minor opposing threat strictly below the mover's threat in the column — it MUST NOT match merely because no opposing threat exists there at all. Additionally, because `detectOvercutVictim` (FR-003) is new code with no prior behavior to characterize (all five sub-case examples above are shaped for the beneficiary role), a sixth counterexample board exercising the victim's losing-mover predicate MUST be added and run through the production detector before that function ships.
- **FR-010**: Lesson 12's copy and any deep-reveal shape-naming text referencing the affected label(s) MUST be updated to match whatever labeling decision is recorded under FR-008.
- **FR-011**: The system MUST add KB cross-references documenting the shipped `detectOvercutVictim`/`detectOvercutBeneficiary` split and the new active-forcing branch to `docs/knowledge-base/community-overcut.md`, `allen-t2.md`, `allen-t4.md`, and `allen-t5.md`.
- **FR-012**: The system MUST fix the live sparring classification path (`classify()`) so that a move which forfeits a forced win is distinguished from a move where the best available outcome was genuinely a draw.
- **FR-013**: The system MUST separately fix the stored/reviewed blunder-tagging path (`tagBlunder`'s Phase E) with the equivalent distinction — fixing FR-012 alone does not satisfy this requirement, since the two paths are independent producers of the same tag.
- **FR-014**: The system MUST record an explicit decision about whether "forfeited a forced win" becomes a new, distinct tag (with its own storage, migration, and backfill of any already-stored data) or remains under the existing `drawing_move` tag with a refined sub-reason/direction field distinguishing the two cases — and MUST justify the choice in writing. This decision MUST also explicitly address the **live sparring path**: the stored `direction` field is not read anywhere on the live path (`classify()`'s sole consumer keys its phrase lookup by tag/category only), so the chosen resolution MUST identify and task the live-path mechanism (e.g. a distinct phrase-pool key) separately from the stored-path fix — fixing only the stored path does not satisfy FR-012. Whichever resolution is chosen MUST also account for `blunderReasons.js`'s composite `tag:direction` keying (`:43` `drawing_move:missed_own`, `:60` bare `drawing_move`). The system MUST trace the call site(s) of the bare-key fallback string at `:60` ("You found the drawing resource — the only move that prevents a loss") and correct it **only if** it is reachable on a forfeited-win (blunder) position — verified at source, this string is used on the optimal/praise path, not the blunder-explanation path, so it may already be correct as written; this requirement is "verify and correct only if reachable," not an unconditional rewrite.
- **FR-015**: Whichever option FR-014 selects, the system MUST update, in the same change, every location that defines, validates, stores, displays, or explains the tag: the database-level constraint governing allowed tag/reason values, the server-side tag registry, the architecture documentation describing tags and their data model, both supported locales' display text, the reason/explanation vocabulary mapping tags to player-facing language, the LLM-context tag list in server code (`explainContext.js`'s hard-coded tag array, e.g. the `'drawing_move'` entry), and the LLM-facing glossary document (`docs/architecture/feature-vector-glossary.md`) describing tag semantics. The server-code tag list and the glossary document are two distinct touchpoints and both MUST be updated — updating one does not satisfy the requirement for the other.
- **FR-016**: The system MUST confirm that the downstream grounding-rule text (Fix 4, from the epic's US2.3) still reads correctly once whichever FR-014 resolution ships, and MUST correct it if it does not.
- **FR-017**: A genuine draw-to-draw position (where the best move and the played move both only draw) MUST continue to receive its current tag unchanged — the fix in FR-012/FR-013 must narrow scope to the forfeited-win case without altering behavior for the correctly-tagged case.
- **FR-018**: The system MUST replace the boolean "did the mover already hold this pattern before their move" gate (used to suppress re-praising a persisting fork) with a comparison of *which* columns/cells hold the pattern before versus after the move, so that a genuinely new, distinct instance of the pattern is recognized as a creation even when an existing instance of the same pattern type was already present.
- **FR-019**: The same per-instance comparison described in FR-018 MUST be applied to the equivalent forced-win creation gate.
- **FR-020**: A move that does not change which columns/cells hold the pattern MUST NOT be reported as a new creation (no regression versus current non-creation behavior).
- **FR-021**: The system MUST add an automated regression that exercises the puzzle-generation pipeline's consumer of this classification tag without invoking the real solver process, so that this consumer's behavior is covered by the fast/CI-safe test suite (the existing end-to-end test for this consumer is excluded from that suite due to solver-process hangs, per project convention).
- **FR-022**: The system MUST decide, and record the rationale for, which of the tactical patterns not currently recognized during live play (figure-7, j-shape, z-threat, undercut, overcut, odd-even-threat, claimeven) are added to live recognition, weighing the per-move latency cost of any pattern whose detection requires a solver call.
- **FR-023**: Every pattern selected under FR-022 MUST be subject to the existing absent→present transition gate (`classifier.js:696`, `if (hasDoubleThreat(nextBoard, player) && !hasDoubleThreat(board, player))`) already used for existing live-praised patterns, so that it is recognized only on first appearance, not on mere persistence — matching the epic's own stated mechanism. This requirement does not depend on FR-018/FR-019 shipping first, and User Story 5 MAY be implemented and shipped independently of, and in either order relative to, User Story 4.
- **FR-024** *(optional, non-blocking)*: Where the per-instance comparison from FR-018/FR-019 is already available for a given pattern (i.e., User Story 4 has already shipped for that pattern's creation-gate family), it SHOULD be preferred over a plain boolean absent→present gate for that pattern's live-recognition gating in FR-023 — but this preference is not a prerequisite for FR-023 and MUST NOT be used to justify building new per-instance infrastructure as part of this epic.
- **FR-025**: For every pattern selected under FR-022, the system MUST confirm the corresponding player-facing phrase pool exists and renders in both supported locales before enabling live recognition for that pattern.
- **FR-026**: Every open issue this epic covers (the specific issue identifiers tracked in the project's open-issues log for: the overcut perspective defect, the overcut taxonomy gap, the forfeited-win mislabeling, the creation-gate residuals, and the live-coach-vocabulary gap) MUST receive a closeout entry in that log in the same change that ships its fix — either marked resolved with a dated status and a description of what shipped and where, or left open with a dated update stating exactly what remains. A textual error in one of these issues' existing description (misidentifying which lesson it refers to) MUST be corrected as part of that issue's closeout. Separately, the forced-win creation-gate's known `blockCol`-sharing collision (see Edge Cases) MUST be recorded as a **new** open-issues log entry, not folded into the existing forced-win creation-gate issue's closeout.
- **FR-027**: The full automated fast test suite MUST pass after every story in this epic, and any documentation describing the reason/tag taxonomy MUST be updated in the same change as the code it describes (not deferred to a follow-up).

### Key Entities

- **Blunder tag**: A stored, player-visible label (plus supporting cell/column metadata) describing a specific mistake a player made in a completed or reviewed game. Read by the review screen, the live sparring coach, and downstream explanation/coaching text.
- **Detector**: A pure or solver-assisted function that inspects a board position and reports whether/where a named tactical pattern (e.g., overcut, undercut, figure-7) currently holds, from a specific player's point of view.
- **Pattern taxonomy label / reason**: The specific sub-case name attached to a detector match (e.g., which T-rule mechanism explains why an overcut holds), distinct from the pattern's top-level name.
- **Fixture**: A committed, human-reviewed example pairing a board position with its expected blunder-tag/detector output, used to pin behavior and catch regressions.
- **Open-issues log entry**: A tracked, numbered record of a known defect or gap, with a lifecycle (open → resolved, or open with dated updates) that this epic's acceptance criteria requires closing out per-item.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: No detector in the codebase computes a tactical-pattern match using one player's board threats together with a different player's score sign — verifiable by inspecting every detector that both reads `scores` and reads perspective-dependent board state.
- **SC-002**: 100% of blunder-tag fixtures affected by the overcut fix have a recorded review (a human confirmation that the new expected value is correct), not merely a passing test.
- **SC-003**: 100% of the documented overcut sub-cases (minor-threat, same-parity/T4, T5 rows-3/6, chain-T2, active-forcing) each have at least one dedicated, passing counterexample test exercised through the production detector.
- **SC-004**: A player who forfeits a forced win in either live play or in post-game review never sees the same label they would see for a genuine best-outcome-is-a-draw position, in either surfaced path.
- **SC-005**: A player who creates a second, distinct tactical fork while already holding one receives the "you just created this" recognition, where today they receive none.
- **SC-006**: Every open issue in this epic's scope shows either a resolved-with-date status or an open status with a dated note of exactly what remains, in the project's open-issues log, by the end of this epic.
- **SC-007**: The full fast/CI-safe automated test suite passes with zero regressions at the end of every user story in this epic.

## Assumptions

- The two-role split pattern already shipped for undercut (`detectUndercutVictim`/`detectUndercutBeneficiary`, dropping `perspective` entirely) is the correct template for overcut, per this epic's Settled decision 1 — the alternative (a child-position solver-recursion route) is explicitly out of scope.
- "Live sparring" and "stored/reviewed blunder analysis" are, and will remain, two independent code producers of blunder tags; this epic does not unify them into one producer.
- The reason-engine's `(bestScore, playedScore)` sign-based case taxonomy is not being changed by this epic — only the *tag* attached to the existing `win_to_draw`-shaped case is in question (User Story 3), not the taxonomy itself.
- Both supported player-facing locales (English and Spanish) must stay in parity for any new or renamed tag/label introduced by this epic.
- "Fast/CI-safe test suite" refers to the project's existing fast test command, which deliberately excludes one specific solver-heavy test file; this epic does not change what is excluded, only adds new coverage that fits within the existing inclusion rule.
- Re-measuring the active `overcut` puzzle/candidate row count is treated as a required verification step, not an assumption — the epic does not assume any particular count going in.

## Open Questions

These are deliberately left open for the planning phase to resolve with the epic owner — they are not to be resolved unilaterally during specification or implementation:

1. **`active_forcing` label naming** (affects User Story 2 / FR-008): does the existing T5 rows-3/6 branch keep the name `active_forcing` (with the new KB-matching branch given a different name), or is the T5 branch renamed (e.g. to something T5-specific) so that `active_forcing` is reserved for the new branch that actually matches the KB's definition of that term? Whichever is chosen must be recorded with rationale in the reason-engine decision log.
2. **Forfeited-win tag taxonomy** (affects User Story 3 / FR-014): should "forfeited a forced win" become a brand-new, distinct tag (requiring its own database-constraint entry, storage, and a backfill of any already-stored `drawing_move`-tagged data that actually matches this case), or should it remain represented under the existing `drawing_move` tag via a refined sub-reason/direction field? Both directions satisfy the user-visible distinction required by FR-012/FR-013; the choice affects migration and backfill scope, not user-facing correctness. Whichever direction is chosen must also resolve the `blunderReasons.js` composite-key hazard (`:43`, `:60`) and its affirmative-praise fallback string, per FR-014.
3. **Live-coach pattern selection** (affects User Story 5 / FR-022): which of the seven candidate tactical patterns (figure-7, j-shape, z-threat, undercut, overcut, odd-even-threat, claimeven) are worth adding to live recognition given each one's latency cost (several require a solver call per move)? This is a scope decision, not a technical unknown, and should be made once the latency of each candidate detector is actually measured.
