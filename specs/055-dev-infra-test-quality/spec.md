## User Scenarios & Testing *(mandatory)*

### User Story 1 - A lint that can actually fail, and covers the whole tree (Priority: P1)

A contributor (human or agent) making a change anywhere in the repo — including a `.mjs` server script or test file — needs `npm run lint` to reliably tell them whether their change introduced a real problem, not drown that signal in 282 pre-existing errors across a glob that silently skips 141 `.mjs` files.

**Why this priority**: Every other quality gate in this repo (tests, CSP, DOM checks) assumes a working lint step exists somewhere in the loop; today it exists but is inert, so a genuinely new defect is invisible in the noise, and an entire file-type sees zero linting regardless of what's in it.

**Independent Test**: Can be fully tested by running `npm run lint` inside `connect-four/` and observing exit code 0 across the whole tree (including `.mjs`/`.cjs`), then deliberately introducing one real violation into a `.mjs` file and observing `npm run lint` fail with that violation reported.

**Acceptance Scenarios**:

1. **Given** the current single-environment `eslint.config.js` with browser globals applied everywhere, **When** the config is split into a browser environment block (`src/`), a node environment block (`server/`, `scripts/`, and `tests/` in general), and a **fourth, narrower** block layering both node and browser globals onto `tests/dom/**` specifically (not all of `tests/`) — because the genuinely bare `document`/`window`/`localStorage` usage lives in exactly 5 files, all under `tests/dom/**` (`research.md` R3), so scoping the merge that tightly means a non-DOM unit test that accidentally reaches for a bare browser global still trips `no-undef`, which is the exact gate this epic exists to build — plus a base/catch-all block so no file in the tree is ever matched by zero blocks (OI-70's exact defect; see FR-018), **Then** environment-mismatch errors (e.g., `no-undef` on `process` in `server/`, or on `document` in `tests/dom/`) disappear without disabling the underlying rule, and every file (including `vite.config.js`, `eslint.config.js`, `public/sw.js`) remains linted by *some* block. **This scoping of browser globals to `tests/dom/**` only, rather than all of `tests/`, is a deliberate DEVIATION from the epic's Settled decision #1** (which assigned the node ruleset to `server/`, `scripts/`, and all of `tests/`) — not a clarification of it; recorded explicitly in `plan.md`'s "Deviations from epic decisions."
2. **Given** the widened `files` glob now includes `.mjs`/`.cjs`, **When** `npm run lint` is run, **Then** it reports a real (freshly measured, not assumed-282) error count for the newly-covered files, and every remaining error across the whole tree is either fixed or explicitly rule-disabled/demoted with a stated reason, per FR-019's explicit triage policy.
3. **Given** `npm run lint` exits 0 on a clean tree, **When** a real violation (e.g., an unused variable) is temporarily inserted into a `.mjs` file, **Then** `npm run lint` exits non-zero and reports that violation — proving the widened glob is actually gated by working rules, not just walked.
4. **Given** `boardToSpec` is imported but never used in `connect-four/src/components/admin/BoardEditor.jsx` (line 4), **When** the unused import is removed, **Then** the corresponding `no-unused-vars` error disappears with no behavior change.
5. **Given** lint now passes cleanly, **When** `eslint . && ` is prefixed onto the `test:fast` script string in `connect-four/package.json` and `sync-kb.mjs`'s existing `.githooks/pre-commit` hook (installed via `package.json`'s `prepare` script; enabled by `git config core.hooksPath .githooks`) is extended to also run lint, **Then** a lint regression fails both `npm run test:fast` and a commit attempt — proven by inserting one violation and observing both gates go red, then reverting.

### User Story 2 - The DOM/unit test suite fails loudly instead of hanging or testing the wrong thing (Priority: P2)

A contributor removing or breaking a guard condition in `Board.jsx`, or touching `SplitReveal`'s live-fit sizing, needs the test suite to report a clear, fast assertion failure — not a 32-second hang that reads as flaky infrastructure, and not a green pass that silently covers nothing.

**Why this priority**: A hang or a vacuous pass is worse than no test at all — it actively misleads whoever encounters it into thinking either "the infra is flaky" or "this is covered," when neither is true.

**Independent Test**: Can be fully tested by (a) deleting `&& value === 'empty'` from `Board.jsx`'s windowCounts guard and confirming `npm run test:dom` now fails with an assertion (not a hang), then reverting the mutation (`Board.jsx` is production code — the deletion is diagnostic only, and `git diff` on it MUST be empty at story completion), and (b) mounting `SplitReveal` in a short container and confirming the new regression test independently catches a spilled/oversized board.

**Acceptance Scenarios**:

1. **Given** the current windowCounts guard mutant hangs `npm run test:dom` for ~32s at 0% CPU, **When** the actual defect (whichever assertion in `BoardWindowCounts.dom.test.jsx` fails to return) is found and fixed, **Then** the same mutant produces a normal, fast assertion failure instead of a hang, and the mutant is reverted from `Board.jsx` afterward (it is a diagnostic, not a real code change).
2. **Given** `specs/042-mistake-review-unification/contracts/split-reveal-zoom-contract.md`'s "Current mechanism" section (lines 6-17) — not the "Required behavior" section, which already describes the *target* frozen-by-signature mechanism, per `research.md` R7 — still describes the superseded pre-fix `boardW`/`>=200`-gate mechanism as if it were current, **When** the section is annotated, **Then** a future reader is told the described behavior is superseded and pointed at the live mechanism, without the contract file itself being rewritten as if it were current.
3. **Given** `splitRevealZoom.test.js` only covers the pure, frozen-by-signature `computeFrozenBoardWidth` and gives zero coverage of the live-fit render bug, **When** a new render-level regression test mounts `SplitReveal` with a short container, **Then** it asserts the rendered board width stays `<=` the pane width and that the `constrain`/`maxWidth` styling stays applied — and this new test is added **by name** to the `test:dom` script string in `connect-four/package.json` and observed running (that script string has no auto-discovery).
4. **Given** `deepRevealPhase` is exported and unit-tested but never called by production code (`DeepRevealPane.jsx` drives the same three states inline via `setTimeout`, importing only the two constants), **When** `deepRevealPhase` is deleted, **Then** only its own test case (`'phase transitions: loading -> slow -> timedOut…'`) is removed from `deepRevealTimeout.test.js`, the sibling test covering the still-live `DEEP_REVEAL_SOFT_MS`/`DEEP_REVEAL_HARD_MS` constants is left intact, and the `test`/`test:fast` script strings are left unchanged (no whole file's worth of coverage moved).

### Edge Cases

- What happens if widening the `.mjs`/`.cjs` glob surfaces an error count large enough that "get to zero" is not achievable within this story's reasonable scope? The story requires triaging the remainder into fix-now vs. an explicitly-justified rule-off, not silently lowering the bar or leaving `npm run lint` red.
- What happens if the OI-71 hang's root cause turns out to be something other than the suspected jsdom/testing-library interaction? The acceptance bar is "the mutant fails with an assertion, not a hang" — whatever the actual root cause, it must be found and fixed, not worked around by weakening the assertion.
- What happens if the production-like build's response headers don't actually carry all expected CSP directives despite the source diff being byte-identical (e.g., a build or serving-configuration gap)? That is a genuine, newly-discovered defect and must be reported, not silently waved through because the source diff looked clean.
- What happens if one of the six closeout-audit issues (OI-1, OI-15, OI-12, OI-24, OI-77, OI-18/36/64 lesson-text half) turns out to still be genuinely open? It must be left open in `docs/open_issues.md` with a dated UPDATE stating exactly what remains — not force-closed to make the audit look complete.
