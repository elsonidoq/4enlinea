# Implementation Plan: Deep Reveal Annotation Integrity Gate

**Branch**: `021-annotation-integrity` | **Date**: 2026-06-04 | **Spec**: specs/021-annotation-integrity/spec.md
**Input**: Feature specification from `/specs/021-annotation-integrity/spec.md`

## Summary

Insert a server-side validate-then-cache gate into `POST /api/explain-move-llm` (between the LLM response and the cache write) that validates every `[zone:...]` annotation against the actual board position using six integrity checks (P1–P6). On failure, retry the LLM once. If the retry also fails, serve a Tier-1 fallback (no zone annotations), log the failure to a new `deep_reveal_failures` table, and skip the quota decrement. Ship a regression harness (unit tests with static fixtures) that replays all known-failing `llm_feedback` rows through the gate.

## Technical Context

**Language/Version**: Node.js 20.10+ (existing)  
**Primary Dependencies**: Express (existing), Supabase JS client (existing, service-role-key). No new npm packages.  
**Storage**: PostgreSQL via Supabase service role key (existing `explanation_cache` table + new `deep_reveal_failures` table via migration 031)  
**Testing**: Jest via `npm run test:fast` (unit-test pattern, no server running, no DB dependency)  
**Target Platform**: Linux server (existing Node.js Express backend)  
**Project Type**: Web service backend  
**Performance Goals**: Gate must complete in under 100ms (regex + small board enumeration). The gate is cheap relative to the LLM call (~2s).  
**Constraints**: Rate limit 5 req/min preserved; retry counts against the same rate limit budget but is transparent to quota; Tier-1 fallback never cached under the Tier-2 position hash.  
**Scale/Scope**: Single Express server, ~5 req/min to the LLM endpoint.

## Plan Corrections

These are resolutions from the spec review that the plan explicitly acknowledges. They override any contradictory text in `spec.md`.

1. **FR-017 reuse directive — spec already corrected**: FR-017 was updated during spec review — the spec now correctly says MUST NOT reuse `getMajorThreatCells`/`checkWin` for 4-window enumeration. Both functions have the wrong semantics (threat detection and win completion, not blocked-vs-live window status). The correct approach: the `Board` class is reused for occupancy data, and 4-window enumeration is a new custom adapter (~25 lines) that enumerates all horizontal/vertical/diagonal windows through each zone cell and checks the blocked-vs-live condition.

2. **Cache write is fire-and-forget (no await)**: The existing `POST /api/explain-move-llm` handler writes to `explanation_cache` without awaiting the promise. This pattern is preserved — zero latency impact on the response. Trade-off: a failed cache write silently skips caching, so the next request for the same position re-calls the LLM. Acceptable at ~5 req/min.

3. **No raw `pg` pool**: The codebase uses Supabase service-role-key client (`supabase.from(...).insert(...)`) for all DB writes, not a raw `pg` pool. All references to "pg pool" in the spec and epic doc are corrected to "Supabase service-role-key client."

## Implementation Sequence

1. **Migration 031** — Create `deep_reveal_failures` table. `CREATE TABLE` only (no GRANT statements); backend-only table, writes via Supabase service-role-key client.

2. **Zone parser extraction** — Extract `zoneParser.js` from `annotatedText.js`, removing `tg` dependency and adding server-only exports (`parseZoneSpecs`, `expandSpec`).

3. **Annotation gate module** — `annotationGate.js` with P1–P6 checks + 4-window adapter.

4. **Regression harness** — `annotationGate.test.js` with static fixture data for all `llm_feedback` rows in the traceability table. P6 uses synthetic pass/fail strings from FR-009 examples (no DB fixtures available).

5. **Endpoint modification — gate, retry, Tier-1 fallback, and quota relocation** — Modify the `POST /api/explain-move-llm` handler in `index.js`:
   - After `callLLM` / `injectDefaultActiveZone` returns, call `annotationGate` on the LLM output against the reconstructed board and parsed zones.
   - **Gate pass**: fire-and-forget write to `explanation_cache` (no `await`, per existing pattern), decrement quota (exactly once), return `{ explanation, prompt, cached? }`.
   - **Gate failure (first attempt)**: retry the LLM once via direct call to `callLLM` (bypassing cache check and quota machinery). Run gate on the retry output.
   - **Retry also fails**: query `explanation_cache` by `position_hash`. Discriminate the Tier-1 row by checking whether `deep_reveal_json.fullText` exists (Tier-1 shape = `{ patternTag, fullText, continuationLine, boardAnnotation }`). If the `.single()` query errors due to multiple rows sharing the same `position_hash` (from both `/api/explain-move` and `/api/explain-move-llm` writes), use `.order('created_at', { ascending: false }).limit(1)` and read the first result row. Extract `fullText`. If no Tier-1 row exists, use static string `"Detailed explanation unavailable."`.
   - **On fallback**: insert a row into `deep_reveal_failures` (via Supabase client). Do NOT cache the invalid output. Do NOT decrement quota. Return `{ explanation: fallbackText, prompt: null, cached?: false }`.
   - Quota is decremented exactly once (not twice on retry success). Zero times on double-failure.

6. **Architecture doc update** — Update `data-model.md` and `server-conventions.md`.
