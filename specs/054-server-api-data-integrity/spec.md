# Feature Specification: Server/API Data Integrity & Environment Correctness

**Feature Branch**: `054-server-api-data-integrity`
**Created**: 2026-08-01
**Status**: Draft
**Input**: User description: "Epic 4 — Server/API Data Integrity & Environment Correctness" (`docs/epics/open-issues-epics.md`, section "## Epic 4"). Close handler-level defects where an identifier, a sort key, or a retry can silently corrupt or leak data, and finish deferred environment/ops verifications that were never runnable in local dev.

## Context this spec inherits (do not re-derive)

This epic closes twelve open issues spanning four independent problem areas: identity/request-context completeness (OI-40, OI-53, OI-17), pagination/retry integrity (OI-47, OI-50), anonymous-cost/serving-pool/outcome integrity (OI-22, OI-49), and environment/ops correctness (OI-5, OI-14, OI-31, OI-51, OI-52). The four user stories below map 1:1 to these areas and are independently testable — none blocks another's implementation.

**OI-49's non-exclusion decision is final, not open.** `GET /api/puzzles/draw` (`connect-four/server/index.js:1640-1665`) filters only on `.eq('category', …)`, `.eq('is_active', true)`, `.not('position','is',null)`, `.order('position')` — it never joins `puzzle_attempts`. This is the deliberate, intended design (never exclude solved/revealed puzzles from the serving pool) and this spec makes **no change** to that query's filtering logic. This is what removes the dependency User Story 3 would otherwise have on User Story 1 landing first — the pool-shape question is already settled.

**The `outcome` enum is narrowed, not widened, and `'tied'` is kept.** `puzzle_attempts.outcome` is currently constrained (migration `003_puzzles.sql`) to `'correct_first' | 'correct_retry' | 'revealed' | 'tied' | 'abandoned'`, but only `'correct_first'` and `'abandoned'` are written by `src/screens/ChallengeScreen.jsx` today. `'tied'` is a live value: `POST /api/puzzles/:id/check` (`server/index.js`, handler at `:2461`) inserts a row with `outcome: evaluation.result`, and `evaluatePredicate` (`server/predicates.js:95`) returns `{ result: 'correct'|'wrong'|'tied' }` — so `'tied'` rows are written today, and Epic 1's multi-column/tied-answer work makes this more common, not less. Because that server writer passes `evaluatePredicate`'s raw vocabulary straight through, its `'wrong'` inserts already fail the *existing* CHECK constraint and are silently dropped by a fire-and-forget `.catch(err => console.error(...))` — an in-scope live defect, not one this epic introduces. The narrowed constraint this epic ships is `'correct_first' | 'tied' | 'incorrect' | 'abandoned'`: it drops `'revealed'` and `'correct_retry'` (never written by any path) and adds `'incorrect'` (a wrong answer, distinct from `'abandoned'`, which is reserved for the user leaving without answering). Dropping `'correct_retry'` means a correct-on-retry attempt is stored as `'correct_first'` even when `moves_tried` is non-empty — this follows the epic's Settled decision #3 and is **not** a defect, but it does make the separately-stored `first_attempt_correct` boolean the only remaining first-vs-retry signal; a future reader must not mistake the enum collapse for a bug. Nothing in the server reads `puzzle_attempts.outcome` values today (the stats aggregate keys off `first_attempt_correct` instead), so this narrowing has no read-side consumers to update beyond docs. `POST /api/user/migrate` (`server/userRoutes.js:501-508`) bulk-imports client-held attempt rows on sign-up; old local rows carry only `'correct_first'`/`'abandoned'`, both of which remain valid under the narrowed constraint, so that path needs no change.

**"Existing rows are not backfilled" has a narrow, specific scope.** It applies only to the unrecoverable `'incorrect'`-vs-`'abandoned'` distinction for historical rows — there is no way to know, after the fact, whether a historical `'abandoned'` row was a wrong answer or a genuine walk-away. It does **not** forbid the mechanical, lossless value remap (`UPDATE` or `NOT VALID` + validate) the migration needs to make any pre-existing non-conforming `outcome` value (e.g. a stray `'revealed'` or `'correct_retry'` row, if any exist) conform before a validating `ADD CONSTRAINT` narrows the CHECK. Whether any such stray rows exist in the live database has not been verified as of this spec; the migration must handle "if any" defensively regardless of what a pre-migration query finds.

**Two `'anonymous'`-literal sites, correctly attributed.** The OI-40 issue text misattributes its own example handler: `POST /api/user/puzzle-attempts` lives at `server/userRoutes.js:343`, opens with `if (!requireUser(req, res)) return;`, and always has a real `req.user.device_uuid` — it needs no fix. The two real fallback-literal sites are `server/index.js:2514` (`const deviceUuid = req.user?.device_uuid || req.body.deviceUuid || 'anonymous';`, inside `POST /api/puzzles/:id/check`) and `server/index.js:1897` (`device_uuid: device_uuid || req.user?.id || 'anonymous'`, in the games-insert payload). `puzzle_attempts.device_uuid` is `text NOT NULL` in the schema, reinforcing that the server must always supply a real value.

**The device identifier is a cross-endpoint join key, not merely a non-shared write value — the identifier must be stable per client, not merely unique per request.** `resolveGameBlunderOwner` (`server/anonBlunderAccess.js:17`) stores anonymous blunders under the game row's `device_uuid`, and `src/screens/ReviewScreen.jsx:152-162` reads them back later via `GET /api/coach/queue?device_uuid=<same local uuid>`, which `resolveQueueOwner` (`anonBlunderAccess.js:29-33`) accepts only if it matches `UUID_RE`. A fresh random UUID minted per request would satisfy "never shared" while orphaning the very rows it wrote — the client could never reproduce the identifier on a later read. This is also why today's `'anonymous'` rows are already orphaned: the literal fails `UUID_RE`. The fix must therefore make the identifier **stable for a given originating client across requests, and reproducible by that client on subsequent reads** — not merely per-request-unique.

**Mechanism: client-supplied identifier first (where one exists), server-minted cookie as fallback.** `src/screens/GameScreen.jsx:60-77` already reads `profile.device_uuid` from the local IndexedDB profile and sends it on the games-insert path (falling back to `''` when no local profile exists) — so `index.js:1897`'s `'anonymous'` literal only trips when the client has no local profile. The Challenge check path does not yet send this identifier at all, and — per Decision 2 below — is **not** changed to start sending one. The fix: server-side, when no identifier arrives with a request (in either fixed site), mint a stable UUID and set it as a cookie (all client fetches already use `credentials: 'include'`), echoing it in the response body so the client's later `coach/queue?device_uuid=` read-back can use the same cookie-carried value. The server must never reject with a 400 in either case. This is a **scoped amendment to the epic's Settled decision #1** ("device identifier is minted server-side") — it extends that decision to also read a client-supplied identifier when one exists (as `GameScreen.jsx` already does), without weakening its intent (never default to a shared bucket, never 400 a live caller).

**Decision 2 (plan-critique step): `ChallengeScreen.jsx` sends nothing; the server-minted `dc4_device_uuid` cookie is the sole mechanism for its two fixed sites.** `ChallengeScreen.jsx` contains **zero** references to `profile`/`getProfile` today — its only identifier-shaped literal is the inert `device_uuid: 'local'` (see below, correctly left unfixed), so it has no existing path to `profile.device_uuid`. Both fetches (`~:511`, `~:603`) already use `credentials: 'include'`, so the server-minted cookie reaches the handler with **no frontend change at all**, and this avoids an async-ordering hazard where the first request could fire before a hypothetical profile load resolves. This keeps the anonymous-identity work server-only, honoring the epic's Settled decision #1 more closely than a client-threading amendment would. The earlier text in this section describing "add `profile.device_uuid` to both request bodies" is superseded by this decision; see FR-001 and the amended Out of Scope § below for the effect on scope.

Separately, `ChallengeScreen.jsx`'s hardcoded `device_uuid: 'local'` literal is **inert** (`SupabaseStore` drops it from the outgoing request body, and `writePuzzleAttempts` sets `device_uuid` from its own server-side parameter, never from client-sent row data) — this spec does **not** task a fix for it; it is not a defect.

**Four `ChallengeScreen.jsx` outcome sites, not three.** Of the pre-existing three `outcome:`-relevant sites, only `~:408` and `~:584` are conditional and currently mislabel a wrong answer as `'abandoned'`. The third, `~:659`, is unconditional and only reached inside the success branch — it has no wrong-answer expression to fix. The sequence-puzzle failure branch (`~:668`) calls `recordPuzzleAttempt` **not at all** today, so sequence-category wrong answers are recorded nowhere — a fourth write call is added there. All line numbers in this spec are approximate per project convention; read each site before editing.

**Ops verifications have real acceptance criteria, not a silent "done".** OI-14 (migration 057 carryover), OI-31 (staging pooler port), and OI-5 (refresh-rotation probe, owner-gated — needs a real account's credentials, not exercisable headlessly) are epic tasks whose sign-off is recorded in `staging_checks.md` (repository root, **not** under `docs/`).

**A worktree that cannot self-derive its ports must fail loudly.** Silently falling back to the main checkout's `3001`/`5173` is the exact port collision the worktree-ports feature exists to prevent (OI-52); today that fallback is silent unless `strictPort` happens to catch a live collision at that instant.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Request context (device identity, user email, terminal-move signal) is always complete and never shared (Priority: P1)

An anonymous player using the app across multiple sessions/devices must never have their puzzle-attempt history silently merged with another anonymous player's, and a signed-in player's checkout flow should not require them to retype an email address the system already has on file for them.

**Why this priority**: Cross-contaminated anonymous history is a data-integrity leak that would silently corrupt analytics and any future per-user feature built on `puzzle_attempts`; it is the epic's highest-severity issue because it is invisible to the user experiencing it.

**Independent Test**: Can be fully tested by sending `POST /api/puzzles/:id/check` and the games-insert path with no `deviceUuid` supplied and confirming the written `device_uuid` is stable for that client across requests and reproducible by that client on a later read (never the literal string `'anonymous'`, and never a fresh value per request); and by confirming a signed-in user's `req.user` carries their email and the Paddle checkout overlay pre-fills it.

**Acceptance Scenarios**:

1. **Given** an anonymous client that omits `deviceUuid` from its request body, **When** it calls `POST /api/puzzles/:id/check`, **Then** the server derives or generates a real, non-shared, stable identifier for the write and returns it to the client — never the literal `'anonymous'` and never a 400 rejection.
2. **Given** an anonymous client whose games-insert payload also omits a device identifier, **When** the games-insert path runs, **Then** it writes the same kind of real, non-shared, stable identifier instead of `device_uuid || req.user?.id || 'anonymous'`.
3. **Given** an anonymous client that has already received a device identifier (client-supplied or server-minted) from a prior request, **When** it makes two successive anonymous writes (e.g. one `POST /api/puzzles/:id/check` and one games-insert), **Then** both writes land under the same identifier, and that identifier is one the client can use to read its own rows back (e.g. via `GET /api/coach/queue?device_uuid=`).
4. **Given** a signed-in user opening the Paddle checkout overlay, **When** the checkout request is built server-side, **Then** the customer email field is pre-filled from the user's account, not left `undefined`.
5. **Given** a fully drawn (full) board, **When** `POST /api/scores` asks `chooseSparringMove` to select a move, **Then** the endpoint returns an explicit terminal signal instead of a response with `col` silently `undefined`.

---

### User Story 2 - Every paginated or retried write is provably safe to repeat (Priority: P2)

An operator or player paging through a long list of games, or an admin re-running candidate generation after a network blip, must get complete, non-duplicated, order-stable results — not silently skipped rows or silently doubled rows.

**Why this priority**: Lower severity than User Story 1 (no data leaks across identities), but still a silent-corruption class of bug — a shuffled or duplicated result set produces wrong answers without any visible error.

**Independent Test**: Can be fully tested by seeding rows that share identical sort-key values, paging through `GET /api/games` and `GET /api/admin/candidates` across separate requests, and confirming no row is skipped or duplicated in either; and by forcing a candidate-insert retry after a simulated post-commit error and confirming no duplicate row lands in `candidates`.

**Acceptance Scenarios**:

1. **Given** multiple `games`/`papergames_games` rows sharing identical values on `GET /api/games`'s current in-JS sort key, **When** the endpoint is paged across separate requests, **Then** every row is returned exactly once, in a stable order, across pages.
2. **Given** a candidate-insert batch whose network call fails after Postgres has already committed the insert, **When** the write path retries, **Then** the retry does not produce duplicate rows in `candidates`, because a unique index on `(generation_run_id, move_string)` makes the duplicate insert a provable no-op (`23505` treated as success).
3. **Given** multiple `candidates` rows sharing an identical `created_at` value (e.g. a generation-run batch insert), **When** `GET /api/admin/candidates` is paged across separate requests, **Then** every row is returned exactly once, in a stable order, across pages.

### User Story 3 - Anonymous review cost is bounded and puzzle-attempt outcomes are recorded accurately (Priority: P2)

An anonymous player re-opening a game review should not force a redundant full re-analysis, and every player's wrong Challenge answer — including on sequence puzzles, which record nothing today — should be distinguishable from simply walking away without answering.

**Why this priority**: Bounds real compute cost (anonymous re-analysis) and fixes a live, silently-dropped write (the server's non-tied outcome inserts already fail today's CHECK constraint) — both are active defects, not latent risk.

**Independent Test**: Can be fully tested by re-opening the same anonymous game's review twice and confirming the second call short-circuits without re-invoking the solver; and by submitting a wrong answer on each puzzle type (including a sequence puzzle) and confirming the stored `outcome` is `'incorrect'`, never `'abandoned'` and never silently dropped.

**Acceptance Scenarios**:

1. **Given** an anonymous game already analyzed once, **When** the same anonymous caller (matched by `device_uuid` with `user_id IS NULL`) requests analysis again, **Then** the server reconstructs from stored blunders instead of re-running the solver, mirroring the authenticated short-circuit.
2. **Given** `GET /api/puzzles/draw`'s current filtering logic, **When** this epic ships, **Then** that query is unchanged — no attempt-history join, no exhaustion policy, no unseen-first ordering is added.
3. **Given** a wrong answer submitted through `POST /api/puzzles/:id/check`, **When** `evaluatePredicate` returns `'wrong'`, **Then** the row inserted by the server writer stores the enum value `'incorrect'`, not the raw `'wrong'` string, and the insert succeeds (does not fail the CHECK constraint).
4. **Given** a wrong submitted answer on any Challenge puzzle type — single-column, multi-column, and sequence — **When** the client records the attempt, **Then** the stored `outcome` is `'incorrect'`; sequence-puzzle failures, which record no attempt at all today, now record one.
5. **Given** the narrowed `puzzle_attempts.outcome` CHECK constraint, **When** a row is inserted with `'correct_first'`, `'tied'`, `'incorrect'`, or `'abandoned'`, **Then** the insert succeeds; **When** a row is inserted with `'revealed'` or `'correct_retry'`, **Then** the insert is rejected.
6. **Given** any pre-existing `puzzle_attempts` row holding a value the narrowed constraint would reject, **When** the migration runs, **Then** that row is mechanically remapped to a conforming value before the validating constraint is added — the migration does not fail and does not attempt to recover the lost `'incorrect'`-vs-`'abandoned'` distinction for historical rows.

### User Story 4 - Deferred environment and ops risks are verified or fixed, with the result recorded (Priority: P3)

An operator relying on the worktree-isolation guarantee, the account-carryover migration, the staging deploy's database connection, or the refresh-rotation behavior needs each of these either fixed or explicitly, dated-ly confirmed — not left as an untested assumption.

**Why this priority**: Ops/verification work; no user-facing defect is currently observed for three of the five issues (OI-14, OI-31, OI-5 are "unverified", not "known broken"), and the two known-broken items (OI-51, OI-52) are low-probability/cosmetic. Sequenced last because it depends on nothing else in this epic and nothing else depends on it.

**Independent Test**: Can be fully tested by running each verification independently (worktree-ports failure injection from both a worktree and the main checkout; migration 057 apply + carryover quickstart; a real staging migration run; the refresh-rotation probe against a real account) and confirming each result — pass, fail, or fixed — is recorded with a date in `staging_checks.md`.

**Acceptance Scenarios**:

1. **Given** a linked worktree whose `worktree-ports.sh` self-derive fails (missing, non-executable, or throws), **When** the dev server or Vite dev process starts, **Then** it refuses to start rather than silently binding the main checkout's `3001`/`5173`.
2. **Given** the main checkout (not a linked worktree), **When** the same self-derive failure is injected, **Then** the existing legacy-port fallback behavior is unchanged (this fix is worktree-scoped only).
3. **Given** either self-derive helper's `execSync` call, **When** it runs outside an interactive `eval "$(./worktree-ports.sh)"` sourcing, **Then** the ownership-probe stderr lines are no longer printed to the console.
4. **Given** migration 057 applied to a database, **When** the account-carryover quickstart (`specs/048-onboarding-experience/quickstart.md`) is run end-to-end, **Then** an anonymous user's `onboarding_status` is confirmed to persist to their account row on sign-up, and the result is recorded in `staging_checks.md`.
5. **Given** whatever `DATABASE_URL` the staging Railway deploy actually injects for migrations, **When** that URL is checked against the session-vs-transaction-pooler rule, **Then** the staging migration path is confirmed safe or corrected, and the finding is recorded in `staging_checks.md`.
6. **Given** the refresh-rotation probe run against a real account's credentials, **When** it reports rotation-detected or no-rotation, **Then** either the de-dup Map is built (if rotation is detected) or OI-5 is closed (if not), and the result is recorded in `staging_checks.md`.

### Edge Cases

- What happens when a device-identifier-deriving request carries no cookies, no prior session, and no client-supplied `deviceUuid` at all (a first-ever anonymous request)? The server must still produce a real, unique identifier, not fall through to any shared default.
- What happens if a historical `puzzle_attempts` row already holds `'revealed'` or `'correct_retry'` at migration time? The migration must remap it to a conforming value rather than failing or silently dropping the row.
- What happens when `GET /api/games`'s two source tables (`games` and `papergames_games`) each contain a row with an identical sort-key value across a page boundary? The audited/fixed tiebreaker must resolve the tie deterministically so no row is skipped or duplicated.
- What happens when a candidate-insert retry's *first* attempt actually succeeded and only the acknowledgment was lost (a false-negative network error)? The fix must treat the resulting duplicate-key condition as a successful no-op, not a hard failure.
- What happens when the refresh-rotation probe cannot be run at all (no owner credentials available during this epic's execution window)? The story is not blocked on this — see FR-032; the finding must be recorded as "not run" with a reason, not silently omitted from `staging_checks.md`.
- What happens to a signed-in user whose Supabase auth record has no email set? Email pre-fill must degrade to the current "field left blank" behavior, not error.

## Out of Scope

Carried verbatim from the epic's `NOT included` list (`docs/epics/open-issues-epics.md`, Epic 4 section), plus the client-scope boundary as amended by this spec's device-identifier decision:

- Rewriting the analyze pipeline or the solver IPC layer.
- Rewriting `worktree-ports.sh` itself — only its two self-derive consumers (`connect-four/vite.config.js`'s `resolvePorts()` and `connect-four/server/index.js`'s `resolveWorktreePortEnv()`) change. FR-025's `GIT_DIR`/`GIT_COMMON` check is re-implemented inside each consumer, not extracted from or exported by the script itself.
- The tier/entitlement model (Epic 3).
- Any change to blunder tagging (Epic 2).
- Any solved/revealed exclusion, unseen-first ordering, or exhaustion policy for the puzzle serving pool — OI-49 is resolved as never-exclude, so this is explicitly out of scope, not deferred.
- Backfilling existing `puzzle_attempts` rows to distinguish historical `'incorrect'` from `'abandoned'` — the distinction is unrecoverable for already-written data.
- **Amended client-side scope**: any client-side (`src/`) change beyond the four `ChallengeScreen.jsx` `outcome:`-relevant write sites named in US3 (approx. lines 408, 584, 659, and the sequence failure branch at approx. line 668). **Superseded (Decision 2, plan-critique step)**: the two additional `ChallengeScreen.jsx` request-body touches originally proposed here (adding `deviceUuid` to the `POST /api/puzzles/:id/check` body `~:511` and the `POST /api/puzzles/:id/sequence/move` body `~:603`) are **struck** — the device-identifier fix for these two sites is server-only (a `dc4_device_uuid` cookie via `credentials: 'include'`), per Decision 2 in the "Context this spec inherits" section. This returns the epic's client-side scope to its original "one deliberate exception, four named touch points" shape; no other client-side change is in scope.

## Requirements *(mandatory)*

### Functional Requirements

**User Story 1 — Request context**

- **FR-001**: The system MUST replace the `'anonymous'` string-literal fallback at `server/index.js:2514` (`POST /api/puzzles/:id/check`) with an identifier that is **stable for the same originating client across requests and reproducible by that client on subsequent reads** (not merely per-request-unique), preferring a client-supplied identifier (the request body's `deviceUuid`, if a caller ever sends one) and falling back to a server-minted, cookie-backed UUID when none arrives — and never rejected with a 400. **Amended (Decision 2, plan-critique step)**: `src/screens/ChallengeScreen.jsx:511` and `:603` send no `deviceUuid` today and are **not** modified to start sending one — `ChallengeScreen.jsx` contains zero references to `profile`/`getProfile`, so it has no existing path to that value, and threading one in would add an async-ordering hazard (the first request could fire before a profile load resolves) for no correctness gain, since `credentials: 'include'` already carries the server-minted `dc4_device_uuid` cookie on every fetch. The identifier for these two sites is therefore server-minted-cookie-only in practice; the client-supplied-first branch remains in the mechanism for any future/other caller that does send `deviceUuid`, but is not exercised by these two sites.
- **FR-002**: The system MUST apply the same fix (stable, reproducible, non-shared, non-rejecting identifier, client-supplied-first with a server-minted cookie fallback) to the second shared-bucket literal at `server/index.js:1897` (`device_uuid: device_uuid || req.user?.id || 'anonymous'`, the games-insert payload) — this site already receives `profile.device_uuid` from `GameScreen.jsx:60-77` when a local profile exists; only its `''`-fallback gap needs the server-minted cookie. (Unaffected by Decision 2 — `GameScreen.jsx` already has a client-supplied value to send; only `ChallengeScreen.jsx`'s two sites lack one.)
- **FR-003**: The system MUST audit every caller of both fixed endpoints for whether it can omit `deviceUuid`, and document the finding. The real no-`deviceUuid` callers are `ChallengeScreen.jsx:511` (`POST /api/puzzles/:id/check`, body `{ candidateCol, moveHistory, attemptNumber }`) and `ChallengeScreen.jsx:603` (`POST /api/puzzles/:id/sequence/move`) — per Decision 2 above, both remain permanently in this category, relying entirely on the server-minted cookie; `GameScreen.jsx:60-77` already supplies the identifier when a local profile exists, with `''` as its only gap. `SupabaseStore.recordPuzzleAttempt` (`src/store/SupabaseStore.js:69`) posts to `/api/user/puzzle-attempts`, a handler (`server/userRoutes.js:343-344`, `if (!requireUser(req, res)) return;`) that is out of scope for this epic and must not be built against by this audit or by FR-005's tests.
- **FR-004**: The system MUST check whether any existing `puzzle_attempts` or `games` rows already hold the literal `'anonymous'` device identifier (contamination from the pre-fix behavior) and record a decision on whether/how to clean them up.
- **FR-005**: The system MUST add automated tests covering both fixed sites and, for each, both the "identifier supplied" and "identifier omitted" branches.
- **FR-006**: The system MUST thread the signed-in user's email (`data.user.email`, already returned by `authClient.auth.getUser(token)`) into `req.user` inside `loadUser()`, with no new database column required.
- **FR-007**: The system MUST confirm that the Paddle checkout overlay pre-fills the customer email for a signed-in user once FR-006 ships, and MUST confirm no handler elsewhere silently depended on `req.user.email` being absent (e.g. a conditional that only fires when the field is falsy).
- **FR-008**: The system MUST make `chooseSparringMove` (or its endpoint) return an explicit terminal/4xx signal instead of a response containing `col: undefined` when called on a position with no playable columns, and MUST add a regression test for this case.
- **FR-009**: The system MUST document the full `req.user` shape (including the newly added `email` field) in `docs/architecture/api-conventions.md`.

**User Story 2 — Pagination and retry integrity**

- **FR-010**: The system MUST audit `GET /api/games`'s current in-JS sort key (across its merge of `games` and `papergames_games`) for row-level uniqueness and, if it is not unique, add a deterministic tiebreaker (e.g. an `id`-based final sort key), following the rationale already documented for `/api/coach/queue`'s `severity DESC, created_at ASC, id ASC` ordering in `docs/architecture/api-conventions.md` — but the fix MUST be derived from `GET /api/games`'s own two-table JS-merge query shape, not copied verbatim from the single-table SQL case.
- **FR-011**: The system MUST demonstrate (via a test that seeds rows sharing identical values on the pre-fix sort key across a simulated page boundary) that the two-table merge cannot reorder rows across separate paginated requests once the tiebreaker (if needed) is in place.
- **FR-012**: The system MUST make the candidate-insert retry path safe against double-insertion by adding a unique index on `(generation_run_id, move_string)` and treating a retried insert of an already-committed batch as a provable no-op — MUST ship this as a migration plus a test proving a retried insert after a simulated post-commit acknowledgment loss does not produce a duplicate row. **Amended mechanism (Blocking issue 1b, plan-critique step)**: the no-op is achieved via `supabase.from('candidates').upsert(rows, { onConflict: 'generation_run_id,move_string', ignoreDuplicates: true })`, not by catching a Postgres `23505` on a plain `.insert(rows)` call. The literal "catch `23505` as a successful no-op" wording is not viable: the insert at `server/index.js:3002` is a single batched, atomic multi-row `INSERT`, so one `23505` fails the *entire* statement rather than skipping just the duplicate row(s) — the literal mechanism would discard every good row in the batch, not just the duplicate one. `.upsert(..., { ignoreDuplicates: true })` achieves the same intent (idempotent replay is a no-op) without that failure mode, and the unique index this FR already requires is exactly what makes the upsert's `onConflict` target exist. Before the index is created, the system MUST also apply FR-017's discipline to this migration (see FR-012a) — a pre-existing duplicate `(generation_run_id, move_string)` pair (the exact shape OI-50's retry bug produces) would otherwise make `CREATE UNIQUE INDEX` itself fail and block the Railway deploy via `migrate.js`'s `process.exit(1)`.
- **FR-012a**: The system MUST inventory every offset-paginated endpoint in `server/index.js` — the known `.range(...)` sites are `:1654` (`GET /api/puzzles/draw`, randomized offset — not sequential paging, no tiebreaker needed), `:1984` (inside `GET /api/games`, covered by FR-010/FR-011), `:2774` (`GET /api/coach/queue`, already ordered by `severity DESC, created_at ASC, id ASC` — no fix needed), and `:3143` (`GET /api/admin/candidates`, ordered only by `.order('created_at', { ascending: true })` with **no `id` tiebreaker**) — and MUST add a deterministic final sort-key tiebreaker (e.g. `id ASC`) to every endpoint in this inventory that is missing one. `GET /api/admin/candidates` is a required fix: candidates are inserted in generation batches that can share an identical `created_at`, the same failure mode documented for `/api/coach/queue` at `docs/architecture/api-conventions.md:324` (8 of 137 rows unreachable in QA before that endpoint's fix). **Separately (Blocking issue 1)**: before migration 062 (FR-012) creates its unique index, the system MUST query `candidates` on every reachable environment for `(generation_run_id, move_string)` groups with `count > 1`, record the observed count in the migration comment, and include a deterministic dedupe step (keep the lowest `id`, delete the rest) ahead of the `CREATE UNIQUE INDEX` — the same discipline FR-017 already applies to migration 063, now applied symmetrically to 062 rather than being an unexplained asymmetry.
- **FR-012b**: The system MUST add a test for `GET /api/admin/candidates` that seeds rows sharing an identical `created_at` value across a simulated page boundary and confirms no row is skipped or duplicated once the tiebreaker from FR-012a is in place.

### Key Entities

- **Device identifier (`device_uuid`)**: A per-anonymous-client identifier written on `puzzle_attempts` and `games` rows to scope anonymous history to one originating client; must never collapse to a shared literal value.
- **Puzzle attempt**: A row recording one player's (identified or anonymous) submission against one puzzle, including its `outcome` and the moves tried.
- **Outcome**: The stored classification of a puzzle attempt — post-epic, exactly `'correct_first' | 'tied' | 'incorrect' | 'abandoned'`.
- **Open-issues log entry**: A tracked, numbered record of a known defect or gap, with a lifecycle (open → resolved, or open with dated updates) that this epic's acceptance criteria requires closing out per-item.
- **Staging check**: A dated, recorded verification result (pass/fail/fixed) for an ops-level concern that cannot be exercised in local dev, tracked in `staging_checks.md`.

## Assumptions

- `GET /api/puzzles/draw`'s filtering logic is out of scope for change — User Story 3 only confirms and documents its existing (unfiltered) behavior, per OI-49's settled resolution.
- The historical `'incorrect'`-vs-`'abandoned'` distinction for rows written before this epic ships is unrecoverable and is deliberately not backfilled; this is distinct from, and does not block, the lossless pre-migration value remap of any stray non-conforming `outcome` values.
- `ChallengeScreen.jsx`'s inert `device_uuid: 'local'` literal is not a defect and is out of scope for this epic.
- OI-5's refresh-rotation probe requires real account credentials that may not be available during this epic's execution window; the epic's acceptance does not depend on the probe actually running, only on the attempt and its outcome (including "not run") being recorded.
- The four user stories are independently implementable and testable in any order; no story in this epic requires another to land first (this is a deliberate simplification versus the epic's pre-decision state, achieved specifically by keeping `GET /api/puzzles/draw` unchanged).
- Both supported player-facing locales are unaffected by this epic — no new user-facing copy is introduced (the `outcome` enum and device identifiers are server/data-layer concepts, not displayed strings).
- "Fast/CI-safe test suite" refers to the project's two existing fast, non-solver test commands — `npm run test:fast` (deliberately excludes one solver-heavy test file, unchanged by this epic) and `npm run test:dom` (jsdom component tests) — both of which FR-034 gates on, per its amendment; this epic does not change what either excludes.
